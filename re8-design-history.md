# re8 console — design history

**Companion to `re8-console-spec.md` — accompanies specification version 0.1 (2026-07-26).** This document holds the *rationale and resolution history* of the re8 design: every architectural decision with its rejected alternatives, and the two adversarial-review registers that drove the specification to its current state.

**Why it is separate (SOL-H2/D121).** The decision log and gap registers grew to outweigh the normative text, and because they necessarily restate *superseded* values they made contradictions hard to see — several review findings were conflicts between a "resolved" register entry and the section it claimed to resolve. The split enforces one rule:

> **`re8-console-spec.md` states only *current* values. Superseded values, alternatives and the reasoning behind them live here.**

Nothing in this document is normative. Where the two disagree, **the specification wins** — and the disagreement is a defect to be reported.

## 1. Architectural decision log

**Feature set frozen 2026-07** — the three post-gap features (D33 text overlay, D34 PS/2 keyboard, D35 PS/2 mouse + hardware cursor) close the feature set; no further features are planned before the emulator-planning stage.

| # | Decision | Alternatives rejected | Rationale |

| D1 | W65C02S @3.3V, 7.159MHz (master÷3 — D20) | 65C816 (16-bit); eZ80; ColdFire; NOS CPUs | one of two in-production classic-bus CPUs (the 816 being the other); 3.3V kills level shifters; static core enables the debug story |
| D2 | Single custom ASIC (oito) for VDP+APU+mapper | separate sound MCU (ATtiny); VS1053B-class PCM chip; discrete 74-series (GameTank-style) | one chip simplifies BOM; audio adds no pins (PWM+I²S) and only small on-die RAM; differentiation lives in silicon |

| D32 | **On-cart FRAM saves** (battery-free), oito-decoded via a new SAVE_CĒ line (36-pin connector); SD/digital titles save to `.sav` files (decision 2026-07) | battery-backed SRAM; console-side shared NVRAM; EEPROM-only | FRAM is nonvolatile + battery-free + high-endurance (no coin-cell save loss); keeps saves with the game (portable); oito-owned decode keeps carts logic-free; console NVRAM would need allocation logic and tie saves to one unit. Emulator persists a CRC32-keyed `.sav` image |
| D33 | **Text overlay layer** (§6.8): top-priority 1bpp char layer, 40-col 8×8 / 80-col 4×8, 2-bank font RAM + `font_sel`, transparent-bg + opaque-textbox attributes, whole-plane fine scroll; free glyphs via sprites (feature 2026-07) | 640px 8×8 80-col mode (needs a 2nd dot clock); 2000-entry character-OAM for arbitrary per-glyph placement | reuses tile-plane + BG-scroll machinery; no pins / no external parts / no video-timing change; grid ≈ one BG plane of bandwidth; a char-OAM would duplicate the sprite engine at ~16× OAM for a rare need — covered by grid + fine scroll + sprite-glyphs |
| D34 | **PS/2 keyboard via the controller ports** (§9.1): bidirectional PS/2 host in oito on a port's data pins, passive DB9↔PS/2 adaptor, built-in key→joypad injection, `re8.keyboard` SDK + region layout tables (feature 2026-07; host made bidirectional by D35) | dedicated PS/2 connector; active-MCU adaptor; receive-only host | reuses the port + DB9 5V/GND → no new pins/connector; key→joypad map makes every joystick game keyboard-playable for free; bidirectional host (shared with the mouse) also gives keyboard LEDs + clean device auto-detect. Cost: 2 pull-ups + open-drain drive + 5V budget |
| D35 | **PS/2 mouse + fully hardware-rendered cursor + hardware hit-test** (§9.2): oito accumulates deltas → scaled/clamped position → top-most cursor from VRAM tiles + hotspot (1 tile 8×8 / 4 tiles 16×16 — corrected by SOL-B9/D111); game gets move/click/wheel events only; **pick registers report the sprite/BG-cell/tile under the pointer**; mouse-first single-source pointer arbitration; upgrades §9.1 host to **bidirectional** (mouse enable cmd); IntelliMouse wheel, cursor bounds, D-pad/keyboard-driven system pointer, device auto-detect, `re8.mouse` SDK (feature 2026-07) | cursor as a normal sprite (counts against budget); software cursor rendering; CPU-side pixel→cell + bounding-box hit-testing; receive-only PS/2 (can't enable a mouse) | cursor as an independent top layer costs one tile (8×8) or four (16×16 — SOL-B9) and no sprite slot; hardware position/scale/clamp means the game only sees events; **hit-test taps the existing compositor (one comparator + latches) and turns a per-click CPU loop into a register read**; bidirectional is mandatory for the mouse and free-riders keyboard LEDs. Joystick-safety: open-drain drivers released unless a port is positively identified as PS/2 (never contends a controller) |
| D125 | **Post-review verification fixes**: sweep divider made integer (÷200 = 239.70 Hz, not ÷199.75); RAM figure corrected 14.7 → **14.4 KB** (14,704 B); `IRQ_STATUS` declared **edge-latched** (only `STATUS`.0–1 and `INPUT_STATUS`.2 are level); SOL-E4's single-container proposal withdrawn in favour of retaining both dot clocks with `DE` (verification pass 2026-07-26) | shipping the four errors found | ÷199.75 is not realisable in hardware; 14,704 B is 14.36 KB (the 14.7 figure divided by 1000); a level-derived VBLANK bit would re-set the instant it was acknowledged and storm; and the single 426-dot container would have pillarboxed **analog** output too, since the R-2R ladder shares the RGB bus — a product regression the "HDMI-only cost" wording concealed |
| D124 | **Final stale-phrase sweep**: "zero-latency execute-in-place" → "execute-in-place without a preload step"; "digital fan-out costs almost zero current" deleted; reset-state exception list corrected to the one genuinely non-zero default (SOL review 2026-07-26, resolves SOL-H5) | keeping phrases already contradicted elsewhere in the document | three of the review's six had been fixed in passing (I²S-to-CH7035B by D83, STATUS.3 by D110, the accuracy-goal conflict by D119). Of the rest: the named NOR has 70 ns access so "zero-latency" was false, and the real advantage is needing no copy-to-RAM; the fan-out claim contradicted §7's own analog-buffer requirement (SOL-E9 specifies three buffer paths precisely because one source cannot drive five outputs); and listing `CURSOR_CTRL` source = 0 as a reset "exception" was meaningless since 0 is the general reset value |
| D123 | **Standing rule: every performance figure MUST carry a workload or the label "estimate"; cross-machine comparisons removed from the spec; PCM cost restated with its workload (≈2.7–6%)** (SOL review 2026-07-26, resolves SOL-H4) | quoting bare numbers ("3–6%", "1,187 tiles/frame", "negligible", "a few cycles") and cross-ISA comparisons | most of these were already fixed by SOL-E15/B17/H3; what remained was the durable part — a rule that stops the pattern returning. Comparisons to Genesis/Amiga/Lynx are **deleted rather than qualified**: a technical specification has no business comparing itself to hardware it has never been benchmarked against (they survive only in the G28 page punch-list). The CPU MIPS figure is kept but labelled as arithmetic from cycle counts |
| D122 | **RFC 2119 keyword convention adopted (MUST/MUST NOT/SHOULD/MAY for requirements only); flagged intensifiers replaced with measurable limits; systematic conversion deferred to the SOL-H2 split** (SOL review 2026-07-26, resolves SOL-H3) | mixing requirements and commentary in one voice; converting the whole 376 KB document immediately | a reader could not tell what was binding, and the review named the tells exactly — all of which appeared here repeatedly. The bounded, high-value part (convention note + replacing "comfortable", "essentially for free", "zero cost", "harmless", "every display", "a few cycles" with numbers) is done now; a full keyword pass is deferred to the split, when every normative statement is being relocated and can be classified as it moves — avoiding churn on text about to change file |
| D121 | **Document split accepted and specified: normative `re8-console-spec.md` + `re8-design-history.md` (§16/§17/superseded narratives), executed after the SOL review concludes, sequenced with the §J closure package** (SOL review 2026-07-26, resolves SOL-H2) | keeping decisions, gaps and normative text interleaved; performing the split immediately | §16+§17 now outweigh the normative content and restate superseded values, which demonstrably hides contradictions — several SOL findings were conflicts between a "resolved" gap entry and the section it resolved. But restructuring is mechanical, substantial work, and doing it in the closing moments of an 80-item campaign is precisely how new inconsistencies appear; so it is specified with a standing rule (normative text states only *current* values) and scheduled as its own pass |
| D120 | **Status restated as "architecture draft" with an explicit outstanding-work table and the principle that a disposition log records decisions made, not decisions correct** (SOL review 2026-07-26, resolves SOL-H1) | "all 53 register entries dispositioned / sufficient to plan and build / campaign complete" | the review's headline judgement, accepted at the outset: the claim was withdrawn before SOL-A1 was started. The campaign then proved the point — a large share of SOL findings were defects in text previously marked resolved, several introduced by earlier remediation. The final wording is honest in both directions: it does not pretend the spec is unfinished, nor that the qualification and validation dependencies do not exist |
| D119 | **Two named emulator accuracy tiers defined; Tier 1 (compatibility) is the conformance target, Tier 2 (cycle-exact) optional** (SOL review 2026-07-26, resolves SOL-B18) | "non-cycle-perfect" in the front matter alongside "cycle-accurate" in §14.5 | the two statements have contradicted each other since the document's first line and survived every revision. Tiers were already being used informally — SOL-G9 invented "Tier 1/Tier 2" for input timing with nothing to reference — so defining them closes the contradiction *and* gives the accumulated timing decisions (per-pixel palette, line-224 snapshot, pick-pixel sampling, ~2.5 ms input quantisation) one place to live. Golden ROMs validate Tier 1 |
| D118 | **Blitter throughput restated as guaranteed minimums under a defined benchmark (≥1,000 interleaved / ≥350 blanking-only); ~1,187/~406 retired** (SOL review 2026-07-26, resolves SOL-B17) | quoting ~1,187/~406 as though specified | those numbers came from an unstated calculation — no copy mode, tile size, arbitration assumption or concurrent load — and SOL-A8 has since changed the blitter itself, so they describe a machine that no longer exists. A stated workload plus a floor is checkable; everything outside it is labelled an estimate. Same move as SOL-E15: replace a confident number with a specification plus its measurement condition |
| D117 | **Hit-test sampling timing pinned**: sample taken as the raster reaches the pick point; pick coordinates latched at line 0 so mid-frame writes apply next frame; `HIT_STATUS`.5 set on sample and cleared each frame; results readable through VBLANK (SOL review 2026-07-26, resolves SOL-B16) | "once per frame" without a named event | the sampling instant determines which scroll and OAM state the result reflects, so two implementations would otherwise report different tiles under the same pointer. Sampling at the pixel comes free from tapping the compositor; latching coordinates at frame start prevents a mid-frame `PICK_X` write from requesting a point the beam already passed. Deliberately the same idiom as SOL-B7's shadow-OAM timing |
| D116 | **Keyboard FIFO/map rules pinned**: 16-byte FIFO dropping on overflow with a W1C sticky flag; `KBD_MAP_IDX` bit 7 = `E0` extended prefix giving 256 slots; `KBD_MAP_VAL` bit 4 targets `_EXT`; lower port wins with two keyboards; hot-unplug flushes and clears injected bits (SOL review 2026-07-26, resolves SOL-B15) | a one-byte map index; unstated depth, overflow-clear and unplug behaviour | the index was a genuine design flaw, not just a missing number: without an extended flag, `E0 4B` (right arrow) collides with `4B` — and arrow keys are exactly what the D34 injection exists to map. Dropping rather than overwriting preserves partially-consumed sequences; clearing injected bits on unplug prevents a stuck button |
| D115 | **IRQ semantics specified as a state machine**: `IRQ̄ = NOT(any(STATUS & ENABLE))` combinational, masked events still record, unmasking a pending event asserts immediately, same-cycle set beats W1C, all bits level-derived, `INPUT_STATUS`.2 re-latches while the FIFO is non-empty, raster-compare fires at line start with no retroactive firing (SOL review 2026-07-26, resolves SOL-B14) | "oito ORs enabled+pending sources onto IRQ̄" | that phrasing left seven software-observable behaviours undefined. Recording masked events is what makes a source pollable while its interrupt is off (the basis of D44); set-beats-clear avoids silently losing an event to a coincident acknowledgement, at the cost of at most one spurious re-entry; level-derived FIFO status forces handlers to *drain* rather than merely acknowledge, which is the correct contract |
| D114 | **`FONT_ADDR_HI` bit 7 selects the font *write* bank, independent of the display bank; bank-0 writes permitted only while the boot overlay is active** (SOL review 2026-07-26, resolves SOL-B12) | a port hard-wired to the cart bank (G45) | firmware is required to load the region charset into **bank 0**, which the port could not address at all — the feature was impossible as written. Separating write-target from display-target is independently useful (rewrite the cart font while the default is shown). Gating bank-0 writes on the boot overlay is what actually enforces G45's promise that the default font survives for system text, and it reuses an existing one-way state rather than adding a mechanism |
| D113 | **Text char-map given a fixed 80-cell (160-byte) row stride in all modes; 4,480 B region; no wrapping; unsigned scroll shifting up/left; off-screen cells not fetched** (SOL review 2026-07-26, resolves SOL-B11) | "always cols × 28" (D40) with a per-mode stride | `cols` varies 32/40/64/80, so the stride was undefined and a live mode switch would reinterpret the same bytes as a different grid, scrambling the display. A fixed stride means a mode change alters only how many cells are *shown*, never where a cell lives — (col 5, row 3) keeps its address in all four configurations — for at most 4,480 B of 128 KB, partly unused in narrow modes |
| D112 | **Cursor arithmetic fully specified**: 4.4 fixed-point scale (0 ⇒ 1.0) with retained fractions, single-threshold ×2 acceleration, truncate-toward-zero and saturate, Y inversion and overflow-bit discard, D-pad ramp 1→4 px, MOUSE_STATUS self-clearing, X_LO-latched coordinate atomicity, ±127 wheel saturation (SOL review 2026-07-26, resolves SOL-B10) | leaving scale format, acceleration, rounding, clearing and atomicity to implementers | cursor feel is immediately noticeable to players, so divergence here is user-visible rather than academic. Retained fractional remainders are what make slow, fine positioning work; treating scale 0 as 1.0 avoids a frozen-pointer failure; latching on X_LO prevents a mid-read packet from tearing the coordinate pair |
| D111 | **`CURSOR_TILE` is four consecutive row-major tiles in 16×16 mode (4-aligned, low 2 index bits ignored); "one tile" corrected everywhere; no cursor flip** (SOL review 2026-07-26, resolves SOL-B9) | claiming the cursor costs "one VRAM tile" while offering a 16×16 size | plain arithmetic: a 16×16 4bpp image is **128 bytes** and a tile is **32** — the two claims could not both hold, and a cursor rendering 32 bytes of a 128-byte image would be a very visible bug. Row-major quad ordering reuses the multi-tile sprite convention of §6.6 so the system has one layout rule; ignoring the low index bits keeps the fetch trivial; flip is explicitly not provided since a pointer never needs it |
| D110 | **`STATUS.3` sprite-overflow latched through VBLANK — cleared at line 0 or by write-1** (SOL review 2026-07-26, resolves SOL-B8) | clearing at VBLANK start | the flag reported "this frame" yet was erased at the moment the frame became inspectable, so it could only be read by polling during active display — defeating its purpose. This is not cosmetic: per-frame overflow detection is how a game implements **sprite multiplexing** (rotating OAM priority so excess sprites flicker rather than vanish), a standard technique the original semantics would have made unusable. W1C also matches the IRQ_STATUS/INPUT_STATUS idiom and lets a game measure sub-frame regions |
| D109 | **Shadow-OAM snapshot pinned to the start of line 224; DMA effects apply from the cycle the burst completes; mid-frame DMA tearing documented** (SOL review 2026-07-26, resolves SOL-B7) | "once per frame during VBLANK" and "DMA takes effect on the current frame" (D41) | neither identified *when*, and they contradict each other for a DMA issued during active display — where "current frame" holds only for lines not yet drawn. Naming line 224 as the snapshot event makes both the next-frame rule for VRAM-port writes and the immediate-effect rule for DMA exact, and turns mid-frame tearing into documented behaviour rather than a surprise. Both are schedulable events in the existing scanline loop |
| D108 | **`OAM_DMA_OFS` ($4065) added; `OAM_DMA_LEN` semantics pinned (0 = all 128, 129–255 clamp, OFS+LEN wraps within OAM)** (SOL review 2026-07-26, resolves SOL-B6) | a length register alone (D39) | D39 claimed a game moving six sprites pays ~32 cycles instead of 683, but with only a length the DMA can refresh a **prefix** and nothing else — a game whose moved sprites sit at indices 40, 41 and 90 gained nothing. One offset driving both source and destination keeps the shadow buffer and OAM in lockstep without a second register, and makes D39's cost claim true rather than aspirational. Clamping (not wrapping) matches the saturating choice in D99 |
| D107 | **`OAM_DMA_SRC` re-encoded as a 1KB block number (bits 0–3, address = block << 10)** (SOL review 2026-07-26, resolves SOL-B5) | the D39 wording "supplies A15:A10" alongside the formula `(value & $3C) << 8` — which describe different things; documenting the sparse legal set $00,$04,…,$3C | the text and arithmetic contradicted each other, and the shifted form forced callers to pre-shift *and* remember which bits were live, inviting bugs for no benefit. A block number is one shift from an address (`addr >> 10`), and all 16 values are valid since 16KB is exactly sixteen 1KB blocks, so there is no illegal encoding to define. Nothing has been built against the old form |
| D106 | **Y scroll corrected from 9-bit to 8-bit; `$4013`/`$4019` become reserved** (SOL review 2026-07-26, resolves SOL-B4) | keeping a 9-bit Y scroll; repurposing the bit as a plane-height selector or 512px-tall map | the name-table is **256 px tall**, which 8 bits addresses exactly — bit 8 had nothing to point at. (X genuinely needs 9 bits for the 512 px width.) A 512-px-tall plane was considered and rejected: it would double BG name-table VRAM from 4 KB to 8 KB per plane and raise fetch bandwidth for a capability nothing has requested. Leaving the bit reserved keeps that door open at zero cost |
| D105 | **All VRAM address arithmetic wraps modulo 128 KB — one uniform rule** (SOL review 2026-07-26, resolves SOL-B3) | clamping; an "invalid tile" behaviour or error flag; leaving overflow undefined | a 12-bit index alone spans the entire 128 KB, so any non-zero pattern base can carry a high index past 17 bits — this is routine, not exotic. Wrapping is literally what the hardware does (the address bus is 17 bits; the high bits do not exist), so it is free and deterministic, whereas clamping needs comparators that buy nothing. Consolidates what SOL-A8, SOL-B1 and SOL-A12 had each stated separately |
| D104 | **Palette port semantics pinned**: 6-bit masked index, increment only on HI *write* (wrapping 63→0), reads never increment, LO/HI independently visible, and **writes take effect at the next composited pixel** (SOL review 2026-07-26, resolves SOL-B2) | leaving increment/wrap/read behaviour and effect timing undefined | the effect-timing question is player-visible, not merely an implementation detail: per-pixel palette lookup is what makes **mid-scanline palette swaps** work, the classic way to exceed 64 on-screen colours. It also imposes a real constraint on emulators — palette state must be sampled per pixel, since caching it per line silently breaks those effects |
| D103 | **VRAM port semantics pinned**: all eight stride codes (1/2/4/8/32/64/128/256), single post-increment on every read *and* write, **no read buffer**, 17-bit wrap, address latched at access start, independent per-access arbitration (SOL review 2026-07-26, resolves SOL-B1) | "stride select (1/2/32/64/…)" and unstated read/increment behaviour | this is the CPU's only path to VRAM, so an ellipsis where a specification belongs guarantees divergent implementations. Strides are chosen to match real structures (cell, tile row, OAM entry, tile, name-table row). The no-read-buffer rule is called out because NES-style ports *do* buffer, so an implementer with that background would otherwise get it wrong; latching the address at access start makes mid-stall pointer writes harmless |
| D102 | **Emulator input becomes a timestamped `(cycle, device, state)` event queue with a modelled ≈2.5 ms acquisition cadence and two accuracy tiers** (SOL review 2026-07-26, resolves SOL-G9) | "present pad state directly in the registers each frame" | after D66 corrected acquisition to ≈400 Hz, a frame-granular model cannot reproduce sub-frame transitions, mid-frame change-IRQ timing, or a press-and-release inside one frame — and games will rely on the change IRQ, so its timing must match hardware. Modelling the cadence rather than the TH protocol keeps oito's sequencing internal while making the observable timing right, consistent with how raster and blitter events are already scheduled |
| D101 | **Debug-info pipeline marked pending validation; breakpoint/symbol identity is (bank, address); proof fixtures in CI per host; map-file-over-DAP fallback** (SOL review 2026-07-26, resolves SOL-G8) | describing the synthesized-ELF trick as if verified; address-only breakpoint identity | per-bank compilation makes `$8100` exist in all 64 banks, so an address-keyed breakpoint fires everywhere and a DWARF line table cannot express which bank is meant. The probe can shadow `BANK_SELECT` by sniffing $4080 writes it already sees, so bank-qualification costs no signal. Carrying the plan is acceptable *because* the fallback — serving line info from our own map file over DAP — is entirely under our control |
| D100 | **`@irqsafe` subset defined and build-time enforced; handlers set flags, main loop acts; nested IRQs forbidden; dispatcher clobber list published** (SOL review 2026-07-26, resolves SOL-G7) | relying on "event-driven" callbacks without a reentrancy rule | this is the root cause behind SOL-A5, G4 and G6: prog8 parameters live in fixed cells, so a callback entering a routine the main program is already inside overwrites its parameters mid-call. Since callbacks are the SDK's headline feature, the safety property had to be stated and checkable — `@irqsafe` is verifiable by walking the handler's call tree, the same analysis dead-code elimination already performs |
| D99 | **IRQ wrapper saves/restores `BANK_SELECT`; bank-stack updates made SEI/CLI-atomic and saturating; `far_call` forbidden in IRQs and with the save window open** (SOL review 2026-07-26, resolves SOL-G6) | leaving bank state unprotected across interrupts; letting the 8-deep stack wrap silently | three parties now touch `BANK_SELECT` and only oito's PCM steal restored it. An IRQ that switches banks silently corrupts a main-line read — the classic weeks-to-find bug — so the wrapper makes handlers safe by construction. Saturating with a flag beats wrapping, which would corrupt bank state invisibly. The save/restore is deliberately a safety net, not permission: far calls in IRQs still hit prog8's non-reentrant static cells |
| D98 | **System-RAM budget published and §15.1 corrected 15.5 KB → ≈14.4 KB; SDK regions declared so the linker fails on overlap; shadow-OAM kilobyte reclaimed when `re8.sprites` is unlinked** (SOL review 2026-07-26, resolves SOL-G5) | a compile-time overflow promise with no enumerated budget | the check is only meaningful if every consumer is declared, and several were added after the promise was written — above all the **1 KB shadow OAM** made mandatory by D41, which is exactly the 0.8 KB the old "≈15.5 KB usable" figure was missing. Splitting compiler-owned from SDK-owned allocations lets the map fail on overlap and the allocation meter report the true remainder |
| D97 | **"No recursion" restated as "ordinary subroutines are non-reentrant; no automatic recursion, manual recursion possible"** (SOL review 2026-07-26, resolves SOL-G4) | listing "No recursion" as a hard limit | it is not true as written — upstream documents manual recursion with programmer-managed state — and an incorrect entry in the *hard limits* list misleads in a specific direction: a developer porting a recursive algorithm would conclude it is impossible rather than manual. The practical bound is the **256-byte hardware stack**, not the language. Stating non-reentrancy precisely also makes the IRQ caveats of SOL-A5 and SOL-G7 coherent, since they stem from the same property |
| D96 | **Typed-symbol source resolved by selection, not assumption**: capture the pinned compiler's real `-dumpvars` output, then use it if typed / else emit an SDK-generated type table / else patch upstream; versioned schema; symbol identity is **(bank, address)** (SOL review 2026-07-26, resolves SOL-G3) | asserting the dependency was closed while §14.4 said it was unconfirmed | the review correctly identified an acknowledged open dependency wearing a "resolved" label. D27's model is sound; only its data source is unknown, and the fallback (SDK-emitted type table) is mechanical and under our control — so the honest close is a decision procedure plus fixtures, not a claim. ## 2. Gaps & inconsistencies register (resolution history)

*Provenance note:* G1–G29 were derived from the three source conversations. G30–G38 (and expansions of several earlier entries) were added after an external adversarial hardware review (`re8-adversarial-hardware-analysis.md`, 2026-07-19); see §18. **G40–G53 were added by the final technical review (2026-07-25)** — a self-consistency, arithmetic, datasheet and toolchain audit of this document after feature freeze. Unlike G1–G39 (which were largely *inherited* ambiguities), G40–G53 are **defects found in the spec's own resolved text**; several are genuine design conflicts, not wording issues.

### A. Blocking for any emulator (memory/registers/timing)

- **G1 — CPU clock. [RESOLVED 2026-07 — see §3, D20.]** Master clock pinned at **21.47727 MHz** (6× NTSC colorburst); **CPU PHI2 = master ÷ 3 = 7.159 MHz**, synchronous (fixed 3:1). Exact budget: **455 CPU cycles/line, 119,210/frame** (262 × 1,365 master ticks). Corrects the marketed "8 MHz" to ~7.16 MHz (page-update item, G28). Exact raster line-totals/porches → new G39.
- **G2 — ZP $0000–$001F reservation. [RESOLVED 2026-07 — see §5.0.]** Not hardware: zero page is ordinary RAM, decoded by nothing in oito. The "internal chip logic" comment was a misnomer for a **software convention** — the re8 runtime/boot stub reserve these 32 bytes for fast variables (IRQ scratch, VBLANK/frame flags, joypad shadows, VRAM-pointer shadow, bank shadow, runtime pointers), and prog8 allocates from $0020 up. Emulator treats it as plain RAM. A bare-metal program not using the runtime may reclaim it.
- **G3 — Register map. [RESOLVED 2026-07 — see §5.1.]** The three conflicting generations are replaced by a single canonical `$4000–$40FF` map with defined addresses, R/W direction, bit-fields and reset state. Knocks down or advances G4, G6, G13, G14 and gives G5/G27/G37 concrete register anchors.
- **G4 — Audio system. [RESOLVED 2026-07 — see §8, D21.]** The under-powered 4-ch PSG is replaced by a **16-voice APU** (4 enhanced PSG + 8 wavetable + 4 PCM/ADPCM) with a full register file, ADSR envelopes, sweep, 15-bit LFSR noise (defined taps), IMA-ADPCM, on-die wave RAM, ROM-streamed PCM, a stereo mixer at ~48 kHz, and I²S + PWM output — all reachable via the $40A0 indirect port. Fully emulatable. (Marketing "4-channel PSG" now needs updating to the APU — page-refresh item, G28.)
- **G5 — CPU↔VRAM access. [RESOLVED 2026-07 — §5.1 interface + §6.5 arbitration.]** Interface: auto-incrementing VRAM address/data port ($4040–$4044); blitter runs VRAM→VRAM; ROM→VRAM loads are CPU loops through VRAM_DATA; OAM via CPU-RAM→VRAM DMA ($4061). Arbitration: single 21.47 MHz VRAM bus, fixed priority **display > blitter > CPU port**; the CPU may access VRAM any time but is **RDY-stalled** until a free cycle (immediate in blanking, brief stall in active display); the blitter's blanking-only vs interleaved modes are the ~406 vs ~1,187 tiles/frame figures. **Residual (cycle-accurate pass only):** exact fetch schedule and stall counts — not emulator-blocking. *Corollary noted:* "graphics never steal a CPU cycle" is overstated — VRAM_DATA transfers and OAM-DMA do stall the CPU.
- **G6 — Collision semantics. [RESOLVED 2026-07 — §6.6.]** COLLIDE_A/B latch the **first** colliding pair in raster order since the last COLLIDE_CLEAR (A=lower index, B=higher); COLLIDE_STATUS.1 sets on further distinct pairs; collision is on opaque sprite-pixel overlap independent of visual priority; overflow-dropped sprites don't participate. Fully emulatable.
- **G7 — oito pin budget & VRAM capacity contradiction. [RESOLVED 2026-07 — see §6.3.]** The unbuildable 64-pin tally (omitted power/ground, VRAM strobes, syncs, clocks, audio, mapper, controller I/O) and the 64KB-vs-128KB VRAM error (2¹⁷ × 4 bits = 64KB) are fixed by moving to **LQFP-144** with an itemized budget (**116 signal / ~134–138 total** after G47, SOL-A2, SOL-E4 and SOL-E12), an **8-bit VRAM data bus** (VA0–16 + VD0–7 = real 128KB, full blitter bandwidth), and controllers read into oito. Package/pad-ring decision D19; fab-route economics moved to G30.
- **G13 — IRQ status/acknowledge semantics. [RESOLVED 2026-07 — see §5.1.]** IRQ_STATUS ($4002) is **write-1-to-clear** per bit; IRQ_ENABLE ($4001) masks sources; oito ORs enabled+pending onto IRQ̄; the CPU reads IRQ_STATUS to prioritize among coincident sources (no fixed hardware priority). Reads are non-destructive.
- **G14 — Bank register placement. [RESOLVED 2026-07.]** BANK_SELECT is canonically at **$4080** (§5.1), a 6-bit register for the $8000–$BFFF window. The `extsub @ $C000 @bank N` example remains a *separate* error — it names an address in the *fixed* window; banked code/data must live in $8000–$BFFF. `extsub` codegen must target the switchable window and write $4080. (The bank *address* conflict is closed; the example's window error is a documentation fix.)
- **G37 — Sprite overflow & priority contract. [RESOLVED 2026-07 — §6.6.]** Per-line evaluation scans OAM 0→127, keeps ≤32 (lowest index wins), drops the rest and sets STATUS.3; limit is 32 sprites with **no separate pixel/tile budget**; lower OAM index draws on top; six-level priority ladder (sprite/Plane-A/Plane-B × 2 priorities + backdrop) fully specified. (Worst-case wide-sprite fetch bandwidth is a cycle-accurate refinement — G39.)

**— Found by the final technical review (2026-07-25) —**

- **G40 — PCM cartridge streaming vs cartridge addressing. [RESOLVED 2026-07-25 — §8.3, §3, §6.3, §13, D36.]** The conflict was real: the cart is reachable only through **A0–A13 + BANK0–5 = 1 MB** (so 24-bit/16 MB was unreachable), and those address lines are **the CPU's**, so "independent" fetch was impossible. Resolved by making **oito an occasional CPU-bus master**, exactly as the NES DMC does: on FIFO low it asserts RDY (halt) then BE (tri-state CPU), drives A0–A15 + BANK0–5 via **bidirectional address pads**, bursts ~16 bytes from ROM, restores the bank and releases. Address width corrected to **20-bit linear (1 MB)**, top 4 bits reserved. Costs **+2 pins (RDY, BE)** and **~3–6 % of CPU cycles**; in exchange samples may exceed 16 KB and cross bank boundaries. Knock-ons recorded: §3 determinism caveat (455 cycles/line is a *bus* budget), §13 wired-AND RDY/BE shared with the probe (steals held off during jam cycles), §14.2 `play_pcm`/`pcm_suspend`, §15.9a.
- **G41 — Save window address. [RESOLVED 2026-07-25 — §11.4, §5/§5.1, D37.]** No new address space exists, so the save chip **maps over the switchable window**: with `SAVE_CTRL.0` ($4081) set, accesses to **$8000–$BFFF** assert **SAVE_CĒ** instead of ROM_CĒ. The 16KB aperture matches A0–A13 exactly; 2KB/8KB parts **mirror** within it (hardware and emulator must alias identically); `SAVE_CTRL.1` is a write-protect defaulting to on; the window is honoured only when the header's has-save flag is set. Code must not execute from $8000–$BFFF while open — the SDK's `re8.save.*` helpers run from the fixed bank and wrap unprotect→open→transfer→close→protect.
- **G42 — Boot-flash paging. [RESOLVED 2026-07-25 — §11.1, §5.1, D38.]** The 8KB overlay now pages the 64–128KB flash via **`BOOT_BANK` ($4008)**: 4 bits select an 8KB page into $E000–$FFFF (16 pages = 128KB), reset 0. **Page 0 is resident** — vectors, page-switch trampoline, core routines — so switching never unmaps running code; pages 1…N hold logo, self-test, screens, region charsets (§6.8), keyboard layout tables (§9.1) and the updater, all read page-locally. `BOOT_BANK` applies only while `BOOT_SRC = 1` (refined by SOL-A1). Emulator: `boot_flash[(BOOT_BANK << 13) + (addr − $E000)]` when `BOOT_SRC=1`; `stub[(addr − $E000) & $7FF]` when `BOOT_SRC=0`.
- **G43 — OAM DMA source size & cost. [RESOLVED 2026-07-25 — §6.6, §5.1, D39.]** The source is now a **1KB-aligned CPU-RAM block** (`OAM_DMA_SRC` holds a block number 0–15; address = `block << 10` — encoding corrected by SOL-B5), matching OAM's 128 × 8 = 1024 bytes — entry size stays 8 bytes because §6.6 uses every bit. Cost pinned: full transfer ≈ **2,048 master ≈ 683 CPU cycles ≈ 1.5 lines**, CPU RDY-stalled, **not abortable**, `OAM_DMA_CTRL`.0 = busy, **issue in VBLANK**. New **`OAM_DMA_LEN` ($4064)** limits the burst to *n* entries (0 = all 128) so partial updates cost proportionally less.
- **G44 — Input/IRQ register inconsistencies. [RESOLVED 2026-07-25 — §5.1, §9, §10.]** All four conflicts closed against the canonical map: (a) §9's superseded gen-C addresses ($4010 JOYPAD_PORT, $4007 buffer read) replaced by **$4070–$4073**; (b) the input-change IRQ correctly identified as **IRQ_STATUS bit 2** (bit 1 is collision); (c) **INPUT_STATUS gains bit 3 = mouse event** (move/button/wheel collectively — the handler reads MOUSE_STATUS $40B0 to distinguish, mirroring the collision pattern), plus a new **`INPUT_IRQ_MASK` ($407B)** giving per-source interrupt enables. *(The mask replaces an earlier sketch that gated mouse IRQs on `CURSOR_CTRL`.0 — that conflated **cursor display** with **interrupt delivery**, so a game couldn't poll a visible pointer or take clicks from a hidden one. Display and IRQ enable are now independent.)* (d) §10's source list restated to the canonical **five** (VBLANK, collision, input change, raster-compare, blitter-done) and the dispatcher contract updated to route through INPUT_STATUS.
- **G45 — Text overlay: cell budget, narrow font, palette. [RESOLVED 2026-07-25 — §6.8, §5.1, D40.]** (a) Budget raised to **2,240 cells (4,480 B)**; the map is always **cols × 28**. (b) Each font bank is now **3 KB** holding *both* densities — 2 KB of 8×8 plus **1 KB of 4×8** (two glyph-rows per byte, starting at bank offset $800); `FONT_ADDR` widens to 12 bits. A 4-wide face is stored, not derived, because column-dropping mangles letterforms. Font RAM 4 KB → **6 KB**; boot flash **3 KB per regional charset**. (c) **`TEXT_CTRL` bits 5–6 select the layer's sub-palette (0–3)**; the attribute's 4-bit index and its background entry both draw from it.
- **G46 — Display-fetch bandwidth & OAM-scan model. [RESOLVED 2026-07-25 — §6.5, §6.6, D41.]** The old "≈80 K display fetch / ≈278 K free" figure was unattainable (BG alone is ~110 K with two planes, and a naive per-line VRAM OAM scan adds 57 K–229 K). Resolved by adding an **on-die 1 KB shadow OAM** — per-line sprite evaluation costs **zero** VRAM accesses, only winners' pattern rows are fetched — and by replacing the estimate with a real table: **display ~175–200 K (~50–56 %), free ~157–182 K** of 357,630. The interleaved blitter (~76 K) still fits, but the margin is now described as **adequate, not large**, and worst-case wide-sprite lines can approach saturation (display always wins). Documented semantic: OAM writes through the VRAM port take effect **next frame**; OAM DMA updates the shadow immediately (exact snapshot timing pinned by SOL-B7).

### B. Hardware-level gaps (needed for faithful behavior modeling)

- **G8 — Caravel RISC-V management core. [RESOLVED 2026-07 — moot.]** The Caravel harness is abandoned (D18/§6.4), so there is no bundled RISC-V core in the console; the question no longer applies.
- **G9 — Audio formats. [RESOLVED 2026-07 — see §8.]** The APU has an internal 16-voice digital mixer producing 16-bit stereo at ~48 kHz (master ÷ 448) → I²S (BCLK/LRCLK/SDATA from the master clock) and delta-sigma PWM. This is the digital source the CH7035B/DAC consume — no PWM-to-PCM conversion problem. **Remaining (minor):** exact I²S MCLK ratio and the physical analog jack type (3.5 mm vs RCA) — board-level, not emulator-blocking.
- **G10 — DVI-D sink handshake & CH7035B behavior. [RESOLVED 2026-07 — §7.1, D31.]** Fixed **1080p60**, CH7035B **Strategy-A self-boot** from EEPROM (Strategy B dropped). **fixed unconditional 1080p60 output with no EDID dependency** (the in-chip-EDID claim is withdrawn by SOL-E5); **CEC not implemented** (fixed-function console; strict DVI carries none). Mode tracking is a non-issue: §6.7 gives both 256/320 H-modes identical line/frame timing, so the CH7035B's input sync is constant and the scaler never reprograms. Custom-timing acceptance + true nearest-neighbor scaling is a **board bring-up verification** item (pin the input to a datasheet-supported RGB mode oito generates; pad the active region if needed) — not emulator-blocking.
- **G11 — Controller scan & change interrupt. [RESOLVED 2026-07 — §9.]** Pad data read into oito (D19/§6.3); oito acquires both ports continuously at **≈400 Hz (≈2.5 ms/acquisition — corrected by SOL-D2, since a 250 µs cadence violates the six-button >2 ms TH-high idle)**, giving ≈2.5 ms worst-case button-to-register latency; the change-IRQ fires on any differing acquisition. Emulator uses the timestamped input-event model (SOL-G9), not per-frame sampling.
- **G12 — 6-button pad protocol. [RESOLVED 2026-07 — §9.]** oito runs the standard Sega multi-step TH-toggle handshake in hardware, auto-detects 3- vs 6-button via the all-low signature step, and exposes the extra X/Y/Z/Mode buttons in JOYPAD_x_EXT; full read completes within the pad's ~1.5ms counter timeout. Transparent to game code and to the emulator.
- **G15 — Expansion header assignment. [RESOLVED 2026-07 — §12.]** Rebalanced to 8 control pins (29–36: PHI2, R/W̄, RES̄, RDY, BE, SYNC, IRQ̄, DBḠ) + 4 power (37–40). Includes IRQ̄; NMĪ is unused system-wide.
- **G16 — Probe bus control & isolation. [RESOLVED 2026-07 — §13.]** Solved inside oito rather than with board glue: oito is the clock master, so on the probe's `DBḠ` it enters debug mode and **pulses PHI2 one cycle per rising edge** (no board clock mux; PHI2 stays an oito output — SOL-C4) and **suppresses all memory/register chip-selects during jam cycles** (no bus contention). The probe owns the bus deterministically by halting via RDY plus oito's chip-select suppression (BE only for true bus mastering — SOL-C3), so live memory access needs no "idle-window" guessing.
- **G21 — Boot ROM / system firmware. [RESOLVED 2026-07 — see §11.1–11.3, D22.]** Two-stage boot: **~2KB internal oito stub (unbrickable) + ~64–128KB external updateable boot flash**. GB-style reset overlay + one-way BOOT_CTRL disable + RAM handoff stub. Firmware does logo/jingle, full system init, self-test combo (= factory test), no-cart/bad-cart screens, cartridge-header validation (new 64-byte header), region/output setup, CH7035B init. Field-updateable via one updater routine delivered three ways (plain update cart / dev cart via probe / SD cart). **Dev bootstrap** = probe fills a writable dev cartridge over the expansion header (no console USB). SD cartridge doubles as the digital-games loader. Emulator may run the boot ROM or fast-boot. (Retires the SST39LF020 BIOS confusion — that part is gone.)
- **G22 — AD725 supply & board rail set. [RESOLVED 2026-07 — §2.1.]** Defined in the power tree: AD725 on 5V, oito core 1.8V, controllers 5V, CH7035B on 1.8V + 3.3V domains (the "~1.2V core" was an error — corrected by SOL-E1); the CPU/memory/logic domain stays a single 3.3V rail.
- **G23 — Reset circuit. [RESOLVED 2026-07 — §2.1.]** A voltage-supervisor/reset controller holds CPU+oito RES̄ until rails are stable and re-asserts on brownout; oito has an internal core PoR; RES̄ on the expansion header.
- **G30 — Full-custom fab route & economics. [CLOSED 2026-07 — out of scope.]** The **route is decided**: oito is full-custom on SKY130 with a custom pad ring in LQFP-144 (D18/§6.4), abandoning Caravel/chipIgnite. The remaining unknowns — specific foundry/MPW engagement, NRE, per-unit cost and MOQ at low-thousands volume (the old Caravel ~$115K / ~$4.50 / 1–5K figures are struck as stale) — are **production-planning economics that belong to a separate document**, not this spec, whose job is design detail sufficient to build an emulator. No emulator dependency; closed here.
- **G31 — DVI-D-vs-HDMI-audio licensing contradiction. [RESOLVED 2026-07 — §7.1/§8.4, D30.]** Resolved by making the digital link **strict DVI-D, video only** — no TERC4 audio, no HDCP, no CEC — so the product emits **zero HDMI-only signalling**. *(The further claim that no HDMI Adopter agreement is therefore required has since been withdrawn as a legal conclusion beyond this document's competence — SOL-E14/D85.)* Audio moves to separate paths: **optical S/PDIF (TOSLINK)** digital out + analog line-out/SCART (§8.4). Factual difference from community MiSTer boards: they emit real HDMI audio; re8 does not. No compliance judgement about third-party products is made here. Scale-up option, if ever wanted: become a low-volume HDMI Adopter ($5K/yr + $1/unit + compliance testing) and enable the CH7035B's HDMI audio — explicitly not the shipping design.
- **G32 — Controller level-shifter. [RESOLVED 2026-07; front-end refined by G51.]** Adopt **74LVC244A** (inputs 5V-tolerant at a 3.3V rail) as the per-port translator feeding oito — *now covering the 4 joystick-only data lines + SELECT only; the 2 PS/2-capable lines need the bidirectional front-end of G51, since a 244 cannot drive*, with per-port series resistors and ESD/TVS protection at the connector (§2, §9, D10). Replaces the incorrect 74HC244.
- **G34 — Persistent storage / save model. [RESOLVED 2026-07 — §11.4, D32.]** Normative save = **on-cart FRAM** (battery-free, ~10¹³ writes), up to 16KB, oito-decoded via a new **SAVE_CĒ** line (connector → 36-pin); EEPROM was allowed as a cheaper option *(removed by SOL-F4)*; **battery-backed SRAM and console-side NVRAM rejected**. Non-saving carts stay one chip. SD/digital titles save to **`.sav` files on the SD** (§11.3). Emulator contract: serialize the save region to a host **`.sav` keyed by ROM CRC32**, distinct from save-states. Header $17 encodes has-save + type + size.
- **G35 — Region / refresh. [RESOLVED 2026-07 — §7, D24.]** **60Hz-only, single global timing.** No 50Hz PAL mode — a deliberate pro-consumer choice (no PAL slowdown; HDMI is region-agnostic 1080p60). Composite/S-Video = NTSC (14.318MHz crystal); RGB SCART/VGA/HDMI are region-agnostic. Header region byte is advisory metadata. Only unsupported case: composite into a 50Hz-only vintage PAL CRT. Flippable to dual 60/50Hz later (adds a timing mode + PAL crystal) if needed.
- **G36 — Power tree. [RESOLVED 2026-07 — §2.1.]** Five rails (5V/3.3V/1.8V/analog-PLL ×2 — the ~1.2V rail is deleted by SOL-E1) from a 9V input via 2 bucks + 2 LDOs (or a PMIC), with a supervisor for PoR/brownout, defined protection (reverse-polarity, fuse, TVS, ESD), and a ~3–5W passive-thermal budget. Exact currents/watts to be confirmed by synthesis + CH7035B datasheet; the rail set and topology are fixed.
- **G39 — Exact raster timing. [RESOLVED 2026-07 — §6.7, D25.]** Both H-modes share one line/frame timing (1,365 master ticks/line = 455 CPU cycles, 15.734kHz HSYNC, 262 lines, **60.055Hz fixed**); only the dot clock changes. Lo-res = 341 dots/line (~5.365MHz: 256 active + 9 FP + 25 sync + 51 BP); hi-res = 426 dots/line (~6.702MHz: 320 active + 14 FP + 32 sync + 60 BP) — the dot clocks are independent PLL outputs (so the non-integer "÷3.2" worry dissolves; dot count per line is exact). Vertical = 224 active + 3 FP + 3 VSYNC + 32 BP. Refresh is a fixed 60.055Hz (no clean 60.00/59.94 exists on an NTSC-locked ÷3 line); CH7035B re-times HDMI to standard 1080p60.

- **G48 — PSG/wavetable pitch floor. [RESOLVED 2026-07-25 — §8.2/§8.3, D42.]** Confirmed design bug: driving the tone dividers from the 21.48 MHz master put the lowest note at **655 Hz ≈ E5** (the formula was NES-derived, where the divisor is the 1.79 MHz CPU clock). Fixed by a **÷12 prescaler — master ÷ 12 = 1.7897725 MHz, exactly the NES APU clock** (shared colorburst ancestry) — plus **12-bit** period fields for pulse and wavetable. Range becomes **27.3 Hz – ~112 kHz**, and NES period tables port unchanged for 11-bit values. The extra bit fit the existing layout (pulse `+1` bit 3 is free outside noise mode; wavetable `+1` bits 3–7 were free), so no register reshuffling. Noise (own rate divider) and PCM (phase accumulator) unaffected.
- **G49 — CH7035B input format mapping. [RESOLVED 2026-07-25 — §7.1, §2, §7, D43.]** Confirmed from the datasheet brief that the part accepts only **RGB-565/666/888** (plus YCrCb), never RGB-444, so oito's 12-bit 4:4:4 bus could not connect as written. Zero cost: fan-out of 2 on 12 traces, no parts, no oito pins; the CH9904 config must select 888. Bring-up items unchanged (custom input timing acceptance, true nearest-neighbor — G10). G29 footnoted: its struck "RGB-565" was probably describing *this* interface, not the palette.
- **G50 — Base-register range vs VRAM size. [RESOLVED 2026-07-25 — §5.1, D44.]** All 2KB-unit base registers are defined as **bits 0–5 significant (64 × 2KB = 128KB); bits 6–7 unwired — ignored on write, read back 0**, so bases always land inside VRAM with no undefined aliasing. `CURSOR_TILE_LO/HI` is pinned as a **12-bit tile index** (byte address = index × 32), matching the name-table and OAM index width.
- **G51 — Keyboard/mouse electrical & rollover claims. [RESOLVED 2026-07-25 — §2, §2.1, §9.1, §15.13.]** (a) The rollover claim was **backwards** and is corrected: **PS/2 is NKRO-capable**; simultaneous-key limits come from the keyboard's own matrix ghosting (it is USB HID boot protocol that is commonly 6-key limited). (b) The 5V figure was restated as a per-port limit with polyfuse protection *(the 500 mA number is corrected by SOL-D7, which separates the 250 mA budget from the 500 mA trip point)* — appropriate now that the DB9 5V pin powers user-supplied devices. (c) The BOM front-end now matches §9.1: the **74LVC244A buffers 4 joystick-only data lines + SELECT**, while the **two PS/2 lines get pull-ups + open-drain drive**, because a unidirectional 244 cannot source the mouse-enable/LED commands. *(The exact circuit — which G51 left as "BSS138-class or a bidirectional shifter" — is specified by SOL-D6.)* No pin-count or joystick-safety change.

### F. Second adversarial review (`re8-sol-adversarial-review.md`, 2026-07-26)

*A second external hostile review, taken from a "reference-emulator contract first, manufacturable prototype second" perspective. It raised ~80 items across blockers (A), register/graphics/IRQ detail (B), CPU-bus/pins/debug (C), controller & PS/2 electrical (D), video/audio/power (E), cartridge/storage (F), toolchain (G) and wording (H), plus a part-verification table (I) and a closure package (J). Items are tracked here as **SOL-xx** and resolved one at a time. **The review's headline judgement is accepted: the previous "all gaps closed / sufficient to build" status was overstated** — see SOL-H1.*

- **SOL-A1 — Internal boot stub was never mapped. [RESOLVED 2026-07-26 — §5.1, §11.1, D45.]** Confirmed contradiction: the stub was said to own the reset vector while reset mapped *external flash* over $E000–$FFFF. Fixed by replacing `BOOT_CTRL`'s single enable bit with a 2-bit **`BOOT_SRC`**: **0 = internal 2KB stub mirrored 4× (reset default, owns $FFFC/D)**, **1 = external boot-flash page** (via `BOOT_BANK`), **2 = overlay disabled** (one-way until RES̄). The stub copies a loader into system RAM — the same trampoline the cartridge handoff uses — then switches to `BOOT_SRC=1` to checksum the firmware, jumping to it if valid. **Recovery** (blank/corrupt flash) returns to `BOOT_SRC=0` and reflashes from an image read **through the cartridge window**, with the debug probe as an alternative path; the mask-ROM stub cannot be erased, so recovery always exists. Mirroring makes every read in the window defined.

- **SOL-A2 — Boot flash had no write strobe. [RESOLVED 2026-07-26 — §6.3, §11.1, §11.3, §2, D46.]** Accepted in full: the G47 recount added `BOOT_CĒ`/`BOOT_ŌĒ` but no **`BOOT_W̄Ē`**, so the "field-updateable firmware" that justifies the whole two-stage brick-safe boot (D22) could not issue NOR program/erase cycles. Added as a **dedicated** pin — explicitly *not* shared with `RAM_W̄Ē`, since a shared strobe would let a mis-decoded stray write program the firmware. Pin budget **114 signal / ~132 total / ~12 spare** (the review predicted these figures). Gated by new **`BOOT_CTRL.BOOT_FLASH_WE`** (bit 2, reset 0), mirroring the `SAVE_CTRL` write-protect idiom. Part named: **SST39VF010, 128KB, 3.3V** — same SST39 family as the cartridge flash, so one **JEDEC** implementation (unlock $5555/$2AAA, 4KB sector erase, byte program, DQ7/DQ6 polling) serves both; the updater runs from RAM because flash cannot be read while programmed.

- **SOL-A3 — Cartridge geometry & save metadata never reached hardware. [RESOLVED 2026-07-26 — §5.1, §11, §11.1, D47.]** The sharpest finding of the review, accepted in full. Three holes: the **fixed window** had to select the last physical bank with no ROM-size register (mis-mapping vectors on *every* sub-1MB cartridge); **`SAVE_CTRL` referenced a header `has-save` bit oito could never see** (a defect introduced by G41/D37, since oito does not parse headers); and the save-size "mirror" had no loading path. Resolved with a boot-programmed, lockable register set — **`CART_CONFIG_BANKS` ($4082)**, **`CART_CONFIG_SAVE` ($4083)**, **`CART_LOCK` ($4084, write $A5)** — filled by firmware from header $16/$17 and locked before handoff. Derived rules now normative: **fixed bank = `bank_count − 1`**; **`BANK_SELECT` masked → out-of-range mirrors** (not open bus); **`BANK0–BANK5` are combinational physical address bits** sourced per access (switchable window / fixed bank / PCM steal). The padding alternative was rejected — it wastes ROM and still leaves save metadata unreachable.

- **SOL-A4 — Unmapped/open-bus behaviour was contradictory. [RESOLVED 2026-07-26 — §5, §5.1, D48.]** The spec gave four different answers ("reserved/open-bus", "reserved/mirror", unlisted registers "read 0", write-only reads undefined) for behaviour that games accidentally come to depend on. Replaced by **one table and one rule: every unmapped read returns $00 and every unmapped write is ignored** — across unlisted `$40xx`, `$4100–$4FFE`, `$5000–$7FFF`, and reads of write-only registers. **Open bus was rejected** as timing-dependent (the classic emulator-divergence source) where a synchronous ASIC can drive $00 for free; **mirroring was rejected** because alias dependencies would freeze future register-space growth. Consequence documented: write-only registers cannot be read back, so software shadows them — which the runtime already does (§5.0).

- **SOL-A5 — IRQ trampoline could not return as described. [RESOLVED 2026-07-26 — §14.4, §10, §5.0, D49.]** A genuine logic error in D26: `JMP ($0014)` is a *jump*, so a prog8 handler's closing `RTS` would pop the **interrupted code's** return address — the documented "return to the trampoline, sample A, restore, RTI" was impossible. Corrected to the standard 6502 indirect-*call* idiom: push `__irq_ret − 1` (high byte first) then `JMP ($0014)`, with full assembly listed in §14.4. ABI pinned: wrapper saves/restores **A, X, Y**; **`CLD` is issued** because 6502 interrupts do not clear decimal mode while prog8 assumes binary; result sampled from **A immediately on return**; **NMI vector points at the address of a real `RTI` instruction**. A self-modifying `JSR` operand was rejected as incompatible with ROM execution (SOL-A6). Re-entrancy of SDK routines called from handlers is explicitly *not* fixed here — see SOL-G7.

- **SOL-A6 — prog8 output not proven ROM-executable. [RESOLVED 2026-07-26 — §14.1, D50; also closes SOL-G1.]** The most consequential finding of the review, since it threatens the *language choice* (D12) rather than a register. Upstream prog8's ordinary output **may contain self-modifying code and inline variables** — harmless for RAM-loaded C64 programs, fatal in a flash cartridge — and ROM-safe output needs **`%option romable`**, which upstream marks **experimental** and which requires BSS in RAM. The spec had never mentioned it. Now normative: `romable` mandatory, **BSS in $0200–$3FFF**, **ROM→RAM copy of initialised mutable data before `main`**, a **build-time gate that fails on any write target outside $0000–$3FFF**, and a **published conformance fixture** (map + startup stub + generated assembly). The version *floor* is replaced by an **exact pin** (prog8 release + commit hash, exact 64tass, JVM) — which also disposes of **SOL-G1**. **Honesty clause added:** prog8 is the *selected* language whose ROM-ability is **pending validation**; if `romable` proves inadequate the fallbacks are a compiler patch or revisiting D12.

- **SOL-A7 — Banked calls & ROM-image construction were unestablished. [RESOLVED 2026-07-26 — new §11.0, §11, §14.1, D51.]** Two real problems, both accepted. (a) `extsub @bank` was asserted by G25/D28 without evidence — upstream implements transparent banked calls only for targets with real bank support and emits target-specific code. **Dependency removed:** re8 uses **SDK `far_call(bank, addr)` wrappers** in the fixed bank; upstream support, if later validated, becomes an optimisation only. (b) A 64KB-address-space compiler cannot build a 1MB banked image, so the **build model is now defined**: one compilation unit per bank + a **post-link packer** that places the fixed bank, fills, emits the map, and writes vectors (reset / `__irq_entry` / real `RTI` for NMI). The review's concrete catch — **`pc_start=8000` colliding with the 64-byte header at CPU $8000–$803F** — is fixed by moving bank-0 code to **`pc_start=$8040`**. Required conformance tests recorded: nested far calls, bank-stack overflow, far calls from IRQs (**forbidden**), far calls with the save window open (**forbidden**).

- **SOL-A8 — Blitter not emulatable from the register description. [RESOLVED 2026-07-26 — §5.1, §6.5, §6.1, §14.2, D52.]** All eleven undefined behaviours pinned with pseudocode in §6.5: linear 17-bit addressing **wrapping mod 128KB**; new **`BLIT_SRC_PITCH`/`BLIT_DST_PITCH`** (without which only contiguous runs could be copied) and **`BLIT_MASK_SRC`** (the missing "where the mask resides" — 1bpp, MSB = leftmost); `BLIT_MODE` bits 0–1 restated as a proper **enum** (copy / transparent / fill / masked) instead of an enum-flag mixture; **W or H = 0 is a NO-OP**, not 256; transparency tests **per nibble**; odd start-X/width does **read-modify-write** on the boundary byte; copies run **ascending** so `dst > src` overlap corrupts (caller's responsibility); `BLIT_FILL` uses the low nibble duplicated; **start and register writes while busy are ignored**; the **done IRQ latches on the final byte write**. Separately, **`VIDEO_CTRL` bit 4 ("render mode") is deleted** — the review is right that the blitter writes VRAM and is not a display layer, so the bit never had a defined visible effect; deleting is more honest than inventing one.

- **SOL-A9 — APU not deterministic enough for a reference emulator. [RESOLVED 2026-07-26 — new §8.5, §8.2/§8.3, D53.]** Accepted: layouts without arithmetic cannot produce identical audio. Added **§8.5 "APU reference model (normative)"** — globals enumerated (**16 voice-active flags need two bytes**, as the review noted); ADSR 4-bit rates defined as indices into a 16-entry ticks-per-step **table** (replacing "exponential step tables"); LFSR direction, feedback bit, taps and **seed $0001** with the all-zero state unreachable; sweep clocked at a fixed **239.70 Hz (÷200)** with rate-0 disable and out-of-range mute; wavetable **non-interpolating** with phase reset on key-on; PCM pitch **8.8 fixed-point**, **end address exclusive**, underrun **holds the last sample**; **IMA-ADPCM loop restores the predictor/index snapshot** (without which looped ADPCM drifts); **`current-position` widened 16→20 bits**, fixing a contradiction D36 had introduced; mixer sums into a **20-bit accumulator** and **hard-clamps** (replacing the untestable "soft-clamp"); reset state defined, wave RAM zeroed by firmware; **golden-hash conformance test** specified.

- **SOL-A10 — Text attribute byte was overcommitted. [RESOLVED 2026-07-26 — §6.8, D54; also closes SOL-B13.]** An arithmetic error introduced by G45/D40: three bits cannot encode a 4-bit background entry *plus* inverse *plus* blink. Re-encoded as **fg 4 bits · bg 2 bits (sub-palette entries 0–3) · opaque-bg 1 bit · blink 1 bit**, keeping the 2-byte cell stride (a 3-byte cell would grow an 80×28 map to 6,720 B). **Per-cell inverse dropped** as redundant — fg and bg sit in the same byte, so the author swaps them directly. **Blink defined** (also disposing of SOL-B13): one **global 1 Hz counter, 50 % duty, phase reset on `TEXT_CTRL`.3 rising edge**, so it is emulator-reproducible; the caret shares that counter.

- **SOL-A11 — Cursor bounds could not encode 9-bit X. [RESOLVED 2026-07-26 — §5.1, D55.]** `CURSOR_BOUND_VAL` was one byte claiming "9-bit X via a hi bit" that was never allocated (a D35 error). Fixed by widening **`CURSOR_BOUND_SEL` to 3 bits selecting six fields** (`X0_LO, X0_HI, Y0, X1_LO, X1_HI, Y1`), costing no new addresses. Also pinned: bounds are **inclusive**, and an **invalid rectangle disables clamping** instead of trapping the cursor.
- **SOL-A12 — Hit-test tile IDs were truncated. [RESOLVED 2026-07-26 — §5.1, §9.2, §14.2, D55.]** Tile indices are 12-bit but `HIT_A_TILE`/`HIT_B_TILE` were one byte each, so IDs 256–4095 were unreportable while the SDK promised "the tile under the pointer". Added **`HIT_TILE_HI` ($40CC)** carrying both planes' high nibbles in one register, and the SDK's `hit_tile()` now returns a `uword`. The review's second point is also taken: `HIT_STATUS` bits **3–4 are now a 2-bit winner field** (backdrop / plane B / plane A / sprite), so a game can tell which layer the click landed on rather than only "sprite or not".

- **SOL-A13 — Fast-boot post-init state unspecified. [RESOLVED 2026-07-26 — new §11.1.1, D56.]** Fast-boot pointed at "the documented post-init state", which did not exist — a compatibility fork hiding inside an optimisation, since two emulators could start the same cartridge from different machine states. Both of the review's exits are taken, in order: **(1) the canonical boot image is the normative contract**, and **(2) fast-boot survives but is defined by a handoff-state table generated from that image and required to match it byte-for-byte**. The table covers registers, RAM ($0000–$3FFF cleared), VRAM, palette, font bank 0 (bank 1 undefined), mapper, APU and CPU state (SP/I/D defined, A/X/Y explicitly undefined). Stated consequence: any firmware revision changing the table is **compatibility-relevant and must bump a handoff-state version**.

- **SOL-C1 — PCM bus-mastering also needs `R/W̄`. [RESOLVED 2026-07-26 — §6.3, §8.3, §4, D57.]** A direct hole in D36: WDC specifies that **`BE` tri-states Address, Data *and* R/W̄**, so during a steal the cartridge saw a **floating strobe** while `ROM_CĒ` was asserted — potentially a write into flash. oito's `R/W̄` pad is now **bidirectional and driven read-high for the whole steal** (no extra pin — it was already in the host-bus group). Full bus-master timing pinned: RDY → BE → drive A/BANK/R/W̄ → ROM_CĒ → sample after ≥70 ns → restore bank → **release BE before RDY**, so the CPU never clocks a cycle with its outputs tri-stated.

- **SOL-C2 — W65C02S pull states omitted. [RESOLVED 2026-07-26 — §4, §6.5, D58.]** Accepted: the modern W65C02S has **no internal RDY pull-up and RDY is bidirectional**, since `WAI` drives it low — and re8 has three parties on that line (CPU/`WAI`, oito stalls, probe breakpoints) while §10 actively recommends `WAI`. Added a normative termination table: **RDY open-drain wired-AND with an external pull-up** (so nobody drives high and `WAI` coexists), **BE pulled up** (fail-safe if the probe is absent/unpowered), **IRQ̄** pulled up, **NMĪ and SOB tied high**, **RES̄** pulled up ahead of the supervisor. The review's framing is adopted generally — *"unused" is a design statement, not an electrical connection* — and the implementation constraint that **oito's RDY/BE pads must be open-drain** is recorded for the pad-ring table (SOL-C8).

- **SOL-C3 — Instruction jamming via `BE` was probably unworkable. [RESOLVED 2026-07-26 — §13, §4, D59.]** Accepted: WDC specifies `BE` low tri-states Address, Data **and** R/W̄, and since the data buffer is bidirectional this plausibly disables the CPU's data **input** path — so the CPU could never consume an injected opcode, and the fetch address/SYNC needed to time injection were lost as well. **Corrected design: `BE` stays HIGH during jamming**; contention-freedom comes from oito's **chip-select suppression** (already specified for this purpose in G16), and the probe drives **only D0–D7**. This gives a clean split — **CS-suppression for jamming, `BE` for true bus ownership** (probe, or oito's PCM steal). The review's demand is adopted in full: because this depends on undocumented CPU-internal behaviour, it **MUST be validated on real silicon with published waveforms before RTL freeze**.

- **SOL-C4 — Single-step request path was missing. [RESOLVED 2026-07-26 — §13, §12, D60.]** Accepted: there was one wire (`DBḠ`) and no protocol on it, so "one PHI2 cycle per probe request" was unimplementable — and having the probe drive PHI2 would have contended with oito's own output. Protocol pinned on the existing wire: **`DBḠ` low = debug mode** (PHI2 held low), **each rising edge = advance exactly one PHI2 cycle**, **held high = resume free-running**, with **implicit acknowledgement** via the PHI2 pulse the probe observes. **PHI2 stays an oito output**; entry/exit are sampled at **cycle boundaries** so no cycle is truncated. No new pins — important because the header is fixed at 40 pins and the probe is already I/O-constrained (SOL-C5).

- **SOL-C5 — RP2040 could not connect to the header. [RESOLVED 2026-07-26 — §2, §13, D61.]** Simple arithmetic, accepted: the header carries **36 non-power signals** (16 address + 8 data + 4 JTAG + 8 control) and **RP2040 has 30 GPIO**, before reserving any for status or transceiver direction — the advertised probe feature set was physically impossible. Probe MCU changed to **RP2350B (QFN-80, 48 GPIO, 3× PIO @150 MHz)**: all 36 signals wire **simultaneously** with ~12 pins spare, so address-match-on-SYNC, RDY assertion, data jamming and JTAG all operate concurrently with **no multiplexing** (answering the review's "state which signals are simultaneous"). The faster PIO also adds margin for SOL-C7. Rejected: RP2040 + external latches (adds capture latency exactly where breakpoint timing is tightest) and an FPGA probe (large cost/toolchain jump for an accessory).

- **SOL-C6 — Probe transceivers and power-domain behaviour were absent. [RESOLVED 2026-07-26 — §13, §12, §2.1, D62.]** Accepted in full; three concrete hazards were undefined. Now normative: **74LVC245 transceivers** on A0–A15 and D0–D7 (direction MCU-driven, **default receive**), control lines direct but **open-drain**; **≈33 Ω series damping** on every header signal (unterminated ribbon rings at a 7.16 MHz bus rate); **all `OE` pulled disabled** so an unpowered/resetting probe is **high-Z on every line** — otherwise its protection diodes would clamp 36 lines and could crash a running console; **header-only power with a series Schottky blocking USB VBUS**, preventing a USB-connected probe from back-feeding the console's 3.3 V rail and energising oito/SRAM through their I/O pins while the console is off; and a stated **≤300 mA header budget**, now included in the 3.3 V buck sizing.

- **SOL-C7 — Breakpoint timing needed proof, not "within nanoseconds". [RESOLVED 2026-07-26 — §13, D63.]** Agreed that the phrase was marketing rather than engineering. A real budget is now published: t<sub>ADS</sub> ~30 ns + ribbon/transceiver ~15 ns + PIO detect ~14 ns + open-drain edge ~20 ns ≈ **79 ns**, against **~70 ns** available before PHI2 falls — so **same-cycle stopping is not achievable and is no longer claimed**. The probe instead asserts **RDY for the following cycle** (full 139.7 ns, comfortable margin); the documented consequence is that the CPU halts having *fetched* the breakpoint opcode, with the PC reported from the latched fetch address — ordinary bus-level-breakpoint behaviour, invisible to the developer. Logic-analyser validation against real silicon is **mandated before probe-firmware freeze**.

- **SOL-C8 — Approximate pin count is not a sign-off pinout. [RESOLVED 2026-07-26 — §6.3, §2, D19, D64.]** Accepted, with a scope clarification. §6.3 is now explicitly labelled a **signal budget** answering only *"does this fit LQFP-144?"* — yes, at **115 signal + ~18–22 power/ground = ~133–137 of 144, 8–12 spare** (the word "comfortable" removed per SOL-H3). Power/ground is now **derived and shown** (≥1 VDD/VSS pair per ~8 simultaneously-switching outputs, plus core pairs, plus an isolated PLL pair) rather than asserted as "~18". A true pad-ring specification depends on the foundry I/O library, ESD strategy, SSO current and bond-wire inductance — unavailable until the §6.4/G30 fab route is engaged — so the **full 144-pin table is recorded as an explicit pre-tapeout deliverable**, including per-pin direction *in every bus-ownership state*, pad type (open-drain RDY/BE), drive class, bank supplies, corner cells, no-connects and the exposed-pad decision. `BOOT_W̄Ē`, which the review flagged as already missing, was added under SOL-A2.

- **SOL-D1 — SELECT high not guaranteed at the controller. [RESOLVED 2026-07-26 — §2, §9, D65.]** A genuine electrical bug, not a wording gap. The 74LVC244A is correct for *receiving* 5V controller outputs at a 3.3V rail (G32 stands), but it was also being used to *send* SELECT to a **5V-powered 74HC157**, whose CMOS input needs ≈0.7 × V<sub>CC</sub> ≈ **3.5V** — unreachable from a 3.3V LVC output across rail, load and temperature, making the 3-button multiplex and the entire 6-button handshake unreliable. **Direction now split:** LVC244A inbound; **SELECT driven outbound by a 5V-powered `SN74AHCT125`**, which accepts 3.3V logic (TTL V<sub>IH</sub> 2.0V) and outputs ≈4.9V. One quad package serves both ports with channels spare.

- **SOL-D2 — 4 kHz polling violated the six-button idle requirement. [RESOLVED 2026-07-26 — §9, D66.]** Accepted; this invalidates a figure I set in G11. Sega's acquisition sequence requires **TH high for >2 ms between acquisitions** so the pad's internal counter resets — a 250 µs cadence never permits it, and both original and clone pads would misreport. Corrected to **≈2.5 ms per port (≈400 Hz)**: ~50 µs for the sequence (8 TH transitions, **≥2 µs settling** each) plus the mandated >2 ms idle. **Worst-case latency restated ≈2.5 ms** (was "≤250 µs") — still well inside a 16.6 ms frame, so the sub-frame conclusion survives with an honest number. One cadence is used for both pad types to keep a single verifiable timing model; validation against original and clone pads is required.

- **SOL-D3 — Six-button sequence prose too loose for RTL. [RESOLVED 2026-07-26 — §9, D67.]** Replaced with a normative **8-sample table** (TH level and D0–D5 meaning per sample), the **≥2 µs settling** rule, and the **active-low-on-wire / active-high-in-register** inversion convention. Identification rules pinned: **6-button ⟺ sample 8 reads D0–D3 = 1111** (structurally impossible for a 3-button pad, which drives D2/D3 low on every TH-low); 3-button ⟺ signature absent; **Master System** pad ⟺ samples do not vary with TH (TH is its Light-Phaser input) → 2-button, EXT = 0; **unplugged** ⟺ idle-high, deliberately indistinguishable from "nothing pressed"; **malformed** → sample-1/2 subset only, EXT never latched with garbage. Counter self-reset (~1.5 ms) plus the >2 ms idle (SOL-D2) guarantees every acquisition starts at state 0.

- **SOL-D4 — PS/2 detection rule was circular. [RESOLVED 2026-07-26 — §9.1, §5.1, D68.]** The sharpest logic error in section D, and mine from G51: transmitters were to stay high-Z "until the port is positively identified as PS/2", while identification was specified as **sending Reset ($FF)** — an action the rule forbids. The review also correctly notes "on a port event" assumed a **plug-detect signal the DB9 does not have**. Replaced by **explicit `PORT_MODE` ($407C)**: ports default to joystick, **oito never transmits except in PS/2 mode**, and the mode is set by the boot firmware's setup menu (persisted in boot flash) or the SDK. A **receive-only `PORT_HINT`** — set when a valid unsolicited 11-bit frame such as the spontaneous BAT `$AA` arrives on a joystick-mode port — recovers most auto-detect convenience **with zero joystick risk, because nothing is ever driven**. Reset/Identify now runs only *after* the port is in PS/2 mode (SOL-D5).

- **SOL-D5 — PS/2 identification sequence was inaccurate. [RESOLVED 2026-07-26 — §9.1, §9.2, D69.]** Accepted: the spec conflated two operations — **Reset ($FF)** returns `$FA` then `$AA` (BAT), while it is **Identify ($F2)** that returns `$AB $83` (keyboard) / `$00` (mouse) / `$03` (wheel mouse) — and none of the surrounding protocol existed. Added a normative state machine: host→device framing (**CLK inhibit ≥100 µs → request-to-send → 11 bits with odd parity → device ACK**), the full identification/enable sequence including the IntelliMouse knock and Set-Scancode-Set-2, and complete error handling — **RESEND ($FE) with a 3-attempt cap, parity-error retry, ~750 ms / ~25 ms timeouts, BAT failure ($FC), and ~2 s hot-unplug detection**. Governing rule: **every failure path releases the transmitters to high-Z**, so a mis-declared port can never contend with a joystick.

- **SOL-D6 — PS/2 open-drain circuit was not actually specified. [RESOLVED 2026-07-26 — §9.1, §2, §9, D70.]** Accepted: G51's "BSS138-class or a bidirectional shifter" named alternatives, not a circuit, and the safety question is entirely topology-dependent. Now exact, per line per port: **4.7 kΩ pull-up to +5 V on the console PCB** (so a bare adaptor cannot float the lines), **1 kΩ series into the 74LVC244A receiver** (limits fault current into the clamp), **BSS138 N-FET pull-down with drain on the 5 V line, source to GND and gate driven by oito's 3.3 V open-drain output**, **≤10 pF TVS**, and a defined power-off state (gate low ⇒ FET off ⇒ line idles high). **oito's pin never sees 5 V in any power state** — deliberately *not* the classic BSS138 bidirectional shifter, whose body diode ties both rails and would give 5 V a path toward the ASIC. Rise-time budget stated: ≈1 µs against a ≥30 µs half-period.

- **SOL-D7 — Port current policy needed connector and fault analysis. [RESOLVED 2026-07-26 — §2.1, §9.1, §15, D71.]** Accepted; the 500 mA/port figure I set in G51 was careless. At 2 × 500 mA the ports would be a **5 W auxiliary load — larger than the console's whole ~3–5 W envelope** — sizing the buck, the 9 V supply and the thermals around accessories nobody ships. Corrected against real draws (pads <10 mA, mouse 20–50 mA, keyboard 100–150 mA): **250 mA per port, 350 mA total**, with **500 mA polyfuse as the *trip* target** — the review's key distinction, since a polyfuse holds at rating and trips above it, so budget ≠ protection. Also pinned: **DB9 contacts (~3 A) are never the limit**; short-circuit trips the port while the console keeps running (explicitly **not** hot-swap-safe); keyboard **inrush** needs buck headroom/soft-start (bring-up item); **backlit/hub keyboards and USB-style high-power devices are out of scope**.

- **SOL-E1 — CH7035B rail specification was wrong. [RESOLVED 2026-07-26 — §2, §2.1, D23, G22, G36, D72.]** A factual error I introduced in D23: the spec invented a **"~1.2 V core"** the part does not require. Per Chrontel's reference design the domains are **1.8 V** (`DVDD`, `AVDD_PLL`) and **3.3 V** (`VDDH`, `AVDD`, `VDDMQ`, `VDDMS`), with **1.2–3.3 V selectable for `VDDIO` only** — and since oito drives 3.3 V RGB (D43), VDDIO is 3.3 V. So the **~1.2 V LDO is deleted**, and the genuinely required **1.8 V domains — which the spec had omitted — are added**, with `AVDD_PLL` on a ferrite-filtered branch mirroring oito's PLL treatment. Recorded caveat (the review's wording, and correct): sharing oito's 1.8 V rail is permitted **only after noise/current/sequencing analysis**, since the scaler's SDRAM interface is a switching load. Net: one fewer regulator and a correct tree.

- **SOL-E2 — CH7035B reset and reference clock were missing. [RESOLVED 2026-07-26 — §2, §2.1, §3, D73.]** Both are consequences of the "Strategy A self-boot" story (D31), which described how the scaler configures itself but never what it needs to *start*: the supervisor reset only CPU and oito, and no timebase existed. Added **`CH7035B_RESETB` to the supervisor group** with the datasheet's requirements — **≥20 ms of stable power before release, ≥100 µs asserted** — plus an ordering constraint the self-boot design implies: the **configuration EEPROM must be powered and stable before `RESETB` releases**, or the scaler boots a blank config. Added a dedicated **27.000 MHz crystal** on XI/XO (conventional for this converter class; divides cleanly to 148.5 MHz for 1080p60), **deliberately independent of the 21.477 MHz master** since the scaler frame-buffers and re-times anyway. The console now has three timebases: 21.477 MHz, 14.318 MHz, 27 MHz.

- **SOL-E3 — CH7035B custom-240p support unproven. [RESOLVED 2026-07-26 — §7.1, D74.]** The largest *risk* item in the review: not a bug, but an unqualified dependency the whole digital-video path rests on, which G10 waved through as a "bring-up item" while treating the part as foundational. Reclassified to **provisionally selected, pending evaluation-board qualification before schematic freeze**, with explicit **go/no-go criteria** (accepts both native modes or the SOL-E4 container; true nearest-neighbour with bilinear disabled; standard 1080p60 out; **latency ≤1 frame** with a stated 60.055→60.000 cadence policy; **CH9904 register image archived** as the normative config artefact). Honouring the review's principle that *a fallback changing image quality must be a selected design*: if native 240p is rejected, **oito line-doubles internally to standard 480p (640×480, 31.47 kHz)** — costed honestly at a **second ~25.175 MHz PLL output** plus the existing line buffer, with image character unchanged. If both fail the part changes and D6 is revisited.

- **SOL-E4 — Mode switching may require scaler reconfiguration. [RESOLVED 2026-07-26 — §7.1, §6.2, §6.3, D75.]** This partly undermines a claim I made in G39/D25. The review is right that **constant HSYNC/VSYNC frequency does not tell a scaler where the active pixels are** — the two H-modes differ in dot clock (5.365 vs 6.703 MHz), total dots (341 vs 426) and active width, and **oito output no DE at all**. Fixed by **adding `DE` to the video bus** (+1 pin) so the active rectangle is explicit rather than inferred from timing. *A first draft additionally forced a single fixed 320-px container with 256-mode pillarboxed; **that was withdrawn on verification (2026-07-26)** — oito drives the analog R-2R ladder from the same RGB bus, so the pillarbox would have appeared on CRT as well as HDMI (256 px would occupy 38.2 µs instead of 47.7 µs), a visible product regression rather than an HDMI-only cost.* **Both dot clocks are retained (§6.7 stands)** and the burden moves to the scaler tracking two geometries from DE — now an explicit **go/no-go item in the SOL-E3 qualification** rather than an assumption, with SOL-E3's line-doubling fallback removing the question entirely if the part cannot.

- **SOL-E5 — EDID/HPD autonomy was overstated. [RESOLVED 2026-07-26 — §7.1, G10, D31, D76.]** Another unsupported capability claim of mine (D31): the public brief describes **HPD as an interrupt to a processor** and **EDID as read through programmed registers** — both presuppose a host, and Strategy A deliberately gives the scaler none. Rather than try to substantiate it, the design **stops depending on EDID**: the scaler drives **1080p60 unconditionally whenever powered**, which is defensible because 1080p60 is the most universally supported digital TV mode and a fixed-function console has nothing to negotiate. **HPD is not acted upon**; if the part needs it to gate TMDS the EEPROM sets free-run. **Failure mode stated plainly:** a sink that cannot take 1080p60 shows nothing digitally — the remedy is the analog outputs. The genuinely missing connector-side requirements are added: **HDMI +5 V pin, DDC pull-ups, HPD level handling, ESD on all TMDS pairs and DDC/HPD**.

- **SOL-E6 — CH9904 size and role misstated. [RESOLVED 2026-07-26 — §2, §7.1, D77.]** Factual correction accepted: **CH9904 is an 8 KB (8192 × 8) I²C boot ROM**, not the "<1 KB configuration device" the BOM claimed — that figure described my estimate of the *register writes*, not the part. Also pinned: the **I²C address `0x57`** from Chrontel's reference design (a generic EEPROM substitute that misses this silently fails), an explicit **substitution rule** (24C64-class 8 KB, matching address, protocol and power-up readiness), and the **configuration binary as a versioned release artefact** (tying to SOL-E3 and the review's closure package). Note the interaction with SOL-E2: a larger EEPROM takes longer to become readable, reinforcing why `RESETB` release must be gated on EEPROM readiness.

- **SOL-E7 — AD725 does not guarantee the specified 240p input. [RESOLVED 2026-07-26 — §2, §7, D78.]** The analog counterpart to SOL-E3: a foundational part used outside its documented envelope. The datasheet specifies **interlaced RGB at TV-standard rates** and discusses equalisation/serration, while re8 supplies **262-line progressive 240p with a plain 3-line VSYNC and no equalisation** — and NTSC's 4-field colour sequence assumes 525-line interlace, so **burst insertion, subcarrier phase and vertical lock are unproven**. Reclassified as **provisionally selected pending bench validation**, with go/no-go criteria that explicitly include **capture devices and upscalers**, which are far less tolerant than CRTs and are how most users will view this output. The **sync waveform is now normative** (negative polarity; equalisation and serration deliberately omitted — the era's "non-interlaced NTSC" convention). **Defined fallback:** interlaced **480i on the AD725 path only**, with the quality change stated rather than hidden; failing that, choose an encoder qualified for 240p. Risk is contained to composite/S-Video — SCART RGB, VGA and HDMI are unaffected.

- **SOL-E8 — CSYNC generation was contradictory. [RESOLVED 2026-07-26 — §6.2, §7, D79.]** Accepted: "XNOR/AND combination of H/V" names two mutually exclusive gates rather than stating an equation, and the spec simultaneously described oito generating CSYNC *and* the AD725 combining H/V internally. Now one path and one equation: **oito generates CSYNC = `NOT(HSYNC XOR VSYNC)`**, with **HSYNC/VSYNC/CSYNC all active-low** — the standard formulation in which horizontal pulses invert during vertical sync (the AND form is simply wrong for active-low signals). The **AD725 receives composite sync on one pin** with its other sync input at the static level, and its internal combination is deliberately unused. Generating CSYNC once in oito also serves **SCART pin 20 and VGA**, so all three analog outputs see an identical waveform — and that waveform (equalisation/serration omitted per SOL-E7) is exactly what the AD725 validation must confirm.

- **SOL-E9 — Active analog video parts missing from an active-component BOM. [RESOLVED 2026-07-26 — §1, §2, §7, D80.]** A real scope contradiction, accepted: §1 declares *all active components* in scope while §7 deferred the analog buffers as "PCB-stage" — even though the text itself admitted one R-2R ladder cannot drive five outputs. **Scope rule corrected** (analog buffering is in scope; only passive values and layout are out), and the stage specified: **one shared R-2R ladder node never loaded directly**, **2× THS7374** (4-channel, integrated filters, 2× gain, 5V) driving SCART and VGA at the standard **0.7 Vₚₚ into 75Ω**, a **separate unity-gain buffer** for the AD725's **~0.714 V AC-coupled** input (a different requirement, hence its own stage), and **SCART pin-16 (1–3V) and pin-8 (9.5–12V) drivers**. Added to the BOM as items 11a–11c and to the 5V rail budget.

- **SOL-E10 — "15 kHz VGA" is a misleading name. [RESOLVED 2026-07-26 — §1, §7, §15, D81.]** Agreed: VGA is 31.5 kHz, so labelling a 15.734 kHz output "VGA" sets exactly the wrong expectation for someone plugging in a PC monitor — which the spec itself said would fail ~95 % of the time. Renamed throughout to **"15 kHz analog RGBHV (DE-15)"**, naming the connector instead of implying a standard we do not meet. The signal is now specified as well: **RGB 0.7 Vₚₚ into 75 Ω**, 75 Ω source termination, **separate H/V on pins 13/14, active-low, 3.3 V logic**, with **CSYNC available on the sync pin as a build option** (free, since oito generates it anyway — SOL-E8) for PVMs and upscalers that prefer it. The corrected wording also feeds the G28 page-refresh punch-list.

- **SOL-E11 — WM8805 violates the no-NOS rule. [RESOLVED 2026-07-26 — §2, §8.4, D82.]** Accepted, and pointedly so: the console's founding constraint is that **every part be orderable new** (§1, philosophy #2), yet the digital-audio path cited a Cirrus part marked **end-of-life** — the one rule this design cannot bend. Replaced with **TI `DIT4192`** (24-bit/192 kHz I²S→S/PDIF transmitter, active production, 3.3 V), with a CPLD/in-oito biphase-mark encoder retained only as a documented alternative (it would cost an ASIC pin and risk). The optical stage is likewise made real: a **current-production 3.3 V TOSLINK transmitter module** with **drive current and series resistor specified**, replacing the unverifiable "TOSLINK module". *(The 47,940.3 Hz vs 48 kHz channel-status question raised alongside this is handled in SOL-E12.)*

- **SOL-E12 — I²S/S/PDIF format unspecified. [RESOLVED 2026-07-26 — §8.4, §6.1, §6.3, §8.1, D83.]** Accepted: the spec said "I²S" without defining one parameter. Now normative and, pleasingly, all derived from the master clock: **LRCLK = master ÷ 448 = 47,940.3 Hz**, **BCLK = master ÷ 7 = 64 × fs** (32 bits/channel), **MCLK = 128 × fs = 6.1364 MHz** PLL-generated on **its own pin** (+1 → 116 signal / ~134–138 total). Format pinned as **standard I²S, MSB first, LRCLK low = left, 16-bit samples left-aligned in 32-bit slots**, oito as clock master. **Channel status:** consumer, copy permitted, no pre-emphasis, 16-bit, **declaring 48 kHz with "level II / variable" accuracy** — the honest encoding for a 47,940.3 Hz stream, since receivers recover the real clock from the biphase signal and track the 0.12 % offset, whereas "not indicated" makes some equipment refuse to lock. The stale claim that I²S feeds the CH7035B is removed: **those pins are physically unconnected to the scaler** (D30).

- **SOL-E13 — Analog audio output needed an active driver. [RESOLVED 2026-07-26 — §2, §8.1, §8.4, D84.]** The audio counterpart of SOL-E9, accepted: "2× PWM → passive RC → jack + SCART" is not a line output — wrong output impedance, no DC blocking, no defined level, and one shared node feeding two destinations that would load each other. Now specified: **PWM defined at last** (2nd-order delta-sigma, 1-bit, **master ÷ 8 = 2.685 MHz** — which also completes the emulator's output model), a **3rd-order active reconstruction filter (−3 dB @ 20 kHz)** built around the driver, an **`NJM4556`-class line driver at 1 Vᵣₘₛ / ≤100 Ω** with **separate series feeds** to the 3.5 mm jack and SCART audio, output coupling for 20 Hz into 10 kΩ with mid-rail bias, **mute until rails and APU are up** (and on brownout) to prevent power-cycle thumps, and inherent short-circuit tolerance. Added to the BOM as item 11d on the 5 V rail.

- **SOL-E14 — Licensing assertions were too absolute. [RESOLVED 2026-07-26 — §7.1, §8.4, §15, D30, G31, D85.]** Accepted, and this one is mine to own: D30 asserted re8 "needs no license **at any volume**" and was "genuinely license-clean" — **legal determinations stated with unearned confidence**. HDMI Licensing Administrator materials treat **connectors and sources as licensed product categories**, not only trademarks and TERC4/HDCP features, so whether DVI-D on a Type-A receptacle avoids every relevant claim is a specialist question. The spec now separates the two: **engineering facts retained** (no TERC4, HDCP, CEC or InfoFrames; DVI-compatible video only; no HDMI name or logo; DVI-D and S/PDIF *commonly described* as royalty-free), while every categorical legal claim is **replaced by "requires counsel and written confirmation before commercialisation."** The characterisation of third-party MiSTer boards as "technically non-compliant" is likewise removed — only the factual difference (they emit HDMI audio, re8 does not) remains. The low-volume-Adopter scale-up path is retained.

- **SOL-E15 — "Every 60 Hz display tolerates 60.055 Hz" was untestable. [RESOLVED 2026-07-26 — §6.7, D86.]** Agreed: an unfalsifiable universal about untested hardware, alongside "CRTs lock fine" and "negligible cadence adjustment". Replaced with a specification — and the digital path actually gains a **stronger** claim: the **CH7035B re-times to exact standard 1080p60**, so the sink never sees 60.055 Hz at all. **Cadence quantified** at ~1 repeated/dropped frame per ~1,100 (≈18 s) rather than called negligible. The analog outputs now carry a **tolerance** — **60.055 Hz ±0.01 %, +0.19 % vs 59.94 Hz; line rate 15.734 kHz ±0.1 %** — and compatibility becomes a **named validation matrix** (consumer CRTs, PVMs, SCART CRTs, RetroTINK/OSSC-class upscalers, capture devices), shared with the SOL-E7 AD725 testing.

- **SOL-F1 — Named flash did not cover the 1 MB maximum. [RESOLVED 2026-07-26 — §2, §11, D87.]** Accepted: the BOM cited only **SST39VF040 (512 KB)** while §11 specifies a **1 MB** maximum, so the named part could not demonstrate the headline configuration — and "Macronix" was a vendor, not a selectable item. Two parts now named: **`SST39VF040` (512 KB, TSOP-32/PLCC-32)** and **`SST39VF080` (1 MB, TSOP-40)**, the larger package being necessary because **20 address lines do not fit 32 pins** — exactly as the review anticipated. Both are 3.0–3.6 V, **70 ns** (inside both the 139.7 ns CPU cycle and the ≥70 ns PCM-steal budget of D57), and in the **same SST39 family as the boot flash (SOL-A2)**, so **one JEDEC driver serves cartridge, boot flash and updater**. Consequence recorded: the cartridge PCB must accommodate the **larger TSOP-40 footprint**, which matters because the shell is a fixed manufactured part.

- **SOL-F2 — SRAMs were not actual BOM parts. [RESOLVED 2026-07-26 — §2, D88.]** Accepted: "16 KB / 128 KB async SRAM, 10 ns, 3.3 V" states requirements, not orderable devices — nothing checkable for production status, package, current or timing. Named: **`IS61C1024AL` (128 K×8, 10 ns)** for VRAM (an exact fit for VA0–VA16) and **`IS61C256AL` (32 K×8, 10 ns)** for system RAM **with A14 tied low so only 16 KB is decoded** — taking the review's point that 32 KB parts are more available than 16 KB. Two consequences stated rather than glossed: **the 16 KB limit remains a *design* limit** (oito's `RAM_CĒ` ignores A14, keeping §15.1 and prog8's `ram_end=3FFF` honest, with no promise about future use of the upper half), and **~30 mA active / <5 mA standby each** joins the 3.3 V budget. Timing margin published — a 139.7 ns cycle makes even **55 ns parts acceptable**, which materially widens sourcing.

- **SOL-F3 — FRAM device protocol matters. [RESOLVED 2026-07-26 — §11, §11.4, D89.]** Accepted, and it produced the most interesting arithmetic of section F. Part named: **Infineon `FM18W08`** (32 K×8, 3.3 V, active production). The substantive correction is the access model — a parallel FRAM requires a **falling `CE` edge for every operation plus a precharge interval**, so **`SAVE_CĒ` is pulsed per access rather than held** across the window, replacing the always-selected SRAM model D37 implied. **Timing checked, not assumed:** 70 ns access / **130 ns cycle** against a **139.7 ns CPU cycle** → one access per cycle, no wait states, **9.7 ns margin** — recorded precisely because it is tight, since the rejected 8 MHz CPU option (125 ns) would have broken it. Density handled per the review's note: 32 KB part, **`A14` tied low**, 16 KB exposed. FRAM saves are 16 KB; the 2 KB/8 KB header codes now belong to the EEPROM path.

- **SOL-F4 — EEPROM could not share FRAM's software contract. [RESOLVED 2026-07-26 — §11.2, §11.4, §15, D32, D90.]** Agreed, and taken further than the review's first option: **EEPROM is removed entirely** rather than specified. Parallel EEPROM's ~5 ms page programs, page rules, **~10⁵ endurance** and **busy polling** cannot share `re8.save.write()`'s immediate contract — and because software can *observe* the busy state, its timing would enter the **compatibility contract**, not merely the BOM, forcing two protocols on every game, the SDK and the emulator. It also contradicts D32's own rationale: at 10⁵ writes a 30-second autosave loop exhausts an EEPROM in about a month, while FRAM effectively never wears out; the BOM saving is small beside shell, PCB, flash and assembly. **FRAM (`FM18W08`) is now the sole save device**, header save-type collapses to **0 = none / 1 = FRAM** (2–3 reserved) with size **16 KB** (smaller codes reserved), and the emulator has a single persistence model with no commit timing to simulate.

- **SOL-F5 — Header checksums underspecified. [RESOLVED 2026-07-26 — §11.2, D91.]** Accepted: both values are **format ABI**, and a packer and boot ROM that disagree reject valid cartridges. **Header checksum ($1A):** 16-bit **byte sum mod 2¹⁶**, little-endian, over **$00–$19 and $1C–$3F**, excluding itself — a plain sum on purpose, so the boot stub verifies it in a few hundred cycles; it guards blankness and corruption, not tampering. **ROM CRC32 ($1C):** the ubiquitous **reflected CRC-32** (0x04C11DB7, init and final-XOR 0xFFFFFFFF) over the **entire padded image with its own field zeroed**, making it a true image identity — which matters because the emulator keys `.sav` files on it (D32); **not verified at boot** (G53). **Header version ($04):** accept if **≤ known**, ignore unrecognised fields, **reject higher versions** rather than guessing.

- **SOL-F6 — Save-file key and initial contents undefined. [RESOLVED 2026-07-26 — §11.4, D92.]** Accepted; all of it is emulator-visible behaviour two implementations would otherwise guess differently. The substantive point is that **FRAM has no erased state** — a fresh `FM18W08` powers up with whatever the die settled at — so the spec declares **virgin contents *unspecified*** and states the consequence: **a game must validate its own save**. Emulator zero-fill of a *new* `.sav` is documented separately as a determinism choice, not a hardware guarantee. File contract pinned: **exactly 16,384 bytes** (short → zero-pad, long → truncate, warn, never fail), key **`<sanitised-title>_<crc32>.sav`** with the CRC **recomputed from the image rather than trusted from the header** (preventing a wrong or malicious value from mis-keying or colliding), and **atomic temp-file + fsync + rename** writes — which matters because games save at precisely the moment users quit.

- **SOL-F7 — Retail NOR writes exposed without a protection policy. [RESOLVED 2026-07-26 — §11, §11.3, §5.1, D93.]** Accepted, including the wording point: an **SST39VF part is in-system programmable**, so calling the retail cartridge "read-only" was inaccurate while the design deliberately **passes writes through** for smart carts — leaving a retail game on live, writable flash where a wild pointer could walk a JEDEC unlock sequence. Protected in silicon: **`CART_WE_ENABLE` (`SAVE_CTRL` bit 4, reset 0)** gates the cartridge write path, set deliberately only by SD/dev/update-cart loaders — the **same reset-cleared idiom as `BOOT_FLASH_WE` (D46) and the save write-protect (D37)**, three gates with one pattern. Belt-and-braces: **retail boards tie `WĒ` inactive at the footprint**, so the part is unprogrammable even if the register were wrongly set. Wording corrected to **"factory-programmed NOR"**. D22's "one connector, no console-side modes" survives because the gate is a register, not a mode.

- **SOL-F8 — "MMC3-style" was misleading. [RESOLVED 2026-07-26 — §1, §6.1, §11, D11, D94.]** Agreed: re8 implements **none** of what defines an MMC3 — no PRG mode switching, no CHR banking, no scanline IRQ counter, no serial register protocol. Renamed throughout to **"console-side fixed-plus-switchable 16 KB mapper"**. The label was not harmless: it implies capabilities we lack and invites "where is the scanline IRQ?", which re8 answers elsewhere (the VDP's `RASTER_CMP`, §5.1). Where lineage is worth noting the spec now says the true thing — the banking model resembles **UxROM**, and the genuinely distinctive choice is that **banking lives in the console rather than the cartridge** (D11), which is why carts are a single chip. Added to the G28 page-refresh punch-list alongside the SOL-E10 renaming.

- **SOL-G2 — Target-property keys unverified. [RESOLVED 2026-07-26 — §14.1, D95.]** A pointed catch: the spec's own G52 entry admitted the `.properties` key spellings were never checked, which made §14.1's "normative command line" **illustrative text presented as specification**. Resolved by removing the assertion rather than guessing: the spec now states only what the target must **achieve** (65C02; RAM $0000–$3FFF; ZP $0020–$007F; `pc_start = $8040`; no launcher; `romable`; symbol dumps), while **the authoritative `re8.properties` lives in the SDK repository as a versioned artefact** the spec links to, with the snippet explicitly labelled illustrative. **CI compiles a minimal game against the pinned toolchain on every change** — the only real validation of key names — sharing a job with SOL-A6's ROM-safety gate and fixture. Added beyond the review: the properties file is **versioned as a pair with the `prog8c` hash**, since an upstream key rename is exactly the drift D28 exists to catch.

- **SOL-G3 — Typed debug symbols remained an open dependency. [RESOLVED 2026-07-26 — §14.4, G52, D96.]** The review correctly identified an **acknowledged open dependency wearing a "resolved" label**: the front matter claimed all gaps closed while §14.4 stated it was unconfirmed whether `-dumpvars` carries types. (The status claim itself was withdrawn under SOL-A1.) Closed by **decision procedure rather than hope**: capture the pinned compiler's **actual** `-dumpvars`/`-dumpsymbols` output as versioned fixtures, then select a source in preference order — **use it if typed**, else **the SDK build emits its own type table** (mechanical, under our control), else a small upstream patch. The adapter consumes a **versioned typed-symbol schema** so compiler drift fails the build visibly. Required coverage includes **banked symbols**, because per-bank compilation (SOL-A7) means the same CPU address exists in several banks — **symbol identity is (bank, address)**, a requirement shared with breakpoint identity (SOL-G8). D27's model is sound; only its data source remains to be confirmed.

- **SOL-G4 — "No recursion" too categorical. [RESOLVED 2026-07-26 — §14.1, §15.2, D97.]** Agreed: what is true is narrower — prog8's **static parameter cells make ordinary subroutines non-reentrant**, so *automatic* recursion is unsupported, but **manual recursion with programmer-managed state is possible** (upstream documents it). The wording mattered because the claim sat in §15, the **hard limits** list, where it would mislead a developer porting a recursive algorithm into thinking it impossible rather than manual. Both sites now use the review's precise formulation, and the spec adds the constraint that actually bites: **the 256-byte hardware stack** bounds manual recursion far more than the language does. Stating non-reentrancy correctly once also makes the related IRQ caveats coherent — **SOL-A5's handler-call caveat and SOL-G7 stem from this same property**.

- **SOL-G5 — RAM accounting needed a real link-map rule. [RESOLVED 2026-07-26 — §5.0, §5, §14.1, §15.1, D98.]** Accepted, and adding it up exposed a stale headline number: the compile-time overflow promise is only meaningful if **every** consumer of the 16 KB is declared, and several were added after it was written — above all the **1 KB shadow-OAM buffer** that D41 made mandatory. **§15.1's "≈15.5 KB usable" is corrected to ≈14.4 KB (14,704 B)**, with a full budget table now in §5.0 splitting **compiler-owned from SDK-owned** allocations (ZP reservation, compiler vars, stack, shadow OAM, keyboard FIFO, callback tables, bank stack, ROM→RAM init data). **SDK regions are declared to the build so the linker/map fails on overlap**, and the allocation meter reports the true remainder rather than the gross 16 KB. One refinement beyond the review: the **shadow-OAM kilobyte is reclaimed automatically** when a game never links `re8.sprites`, via the dead-code elimination the SDK already relies on.

- **SOL-G6 — Bank changes were non-reentrant. [RESOLVED 2026-07-26 — §14.4, §11, D99.]** Accepted: `BANK_SELECT` is global mutable state touched by main-line code, IRQ handlers and **oito's PCM steals** — and only the last was safe (D36 restores it). The failure is concrete and silent: main code selects bank 7, an IRQ switches to bank 3, and on return main code reads bank 3 believing it is bank 7. Fixed by making **`__irq_entry` save and restore `BANK_SELECT`** through the ZP shadow (~8 bytes, ~12 cycles) — safety **by construction, not discipline**. Also pinned: **bank-stack push/pop is SEI/CLI-atomic**, **overflow/underflow saturates and raises an SDK-readable flag** rather than wrapping silently (invisible corruption being the worst outcome), and **`far_call` is forbidden both inside IRQ handlers** — the wrapper is a safety net, not a licence, since handlers still hit prog8's non-reentrant static cells — **and while the save window is open** (§11.0), with debug-build assertions.

- **SOL-G7 — IRQ callbacks conflicted with static parameters. [RESOLVED 2026-07-26 — §14.4, §10, D100.]** The root cause I had deferred to three times (SOL-A5, G4, G6 all pointed here), and the review states it exactly: prog8 parameters live in **fixed cells**, so a callback entering an SDK routine the main program is already inside **overwrites that routine's parameters mid-call** — while event-driven callbacks are the SDK's headline feature. Resolved with an explicit, enforceable rule: handlers may call **only `@irqsafe` routines**, which use no shared parameter cells (arguments in registers or the IRQ-only ZP scratch $00–$01). The safe subset covers what handlers actually need (status/joypad/keyboard/mouse reads, IRQ acknowledgement, flag setting, register pokes) and **excludes `far_call`, `use_data_bank`, `re8.save.*`, `re8.text.put`, blitter helpers and anything taking a string**. The **flag-and-return idiom becomes normative**, **nested IRQs are forbidden**, and the **dispatcher's ZP clobber list is published**. Enforcement is mechanical — walking the handler's call tree, the same analysis dead-code elimination already performs.

- **SOL-G8 — DWARF synthesis is a proposal, not a verified pipeline. [RESOLVED 2026-07-26 — §14.3, §13, D101.]** Accepted, including the structural catch: with per-bank compilation (SOL-A7) the address **`$8100` exists in all 64 banks**, so an address-keyed breakpoint would fire in every one and a DWARF line table cannot express which bank is meant. **Breakpoint and symbol identity is now (bank, address)** — matching SOL-G3 — and the probe qualifies matches on the **shadowed `BANK_SELECT`**, which costs no new signal because it already sniffs the `$4080` writes off the bus. **Proof fixtures are required**: a checked-in sample project validated in **CI per supported host and debugger**, covering line tables, function names, breakpoint set/hit, stepping and banked duplicate addresses. Status marked **pending validation** (like SOL-A6), with a real fallback recorded: if a code-free `clang -g` ELF proves unreliable, the adapter serves line info **from its own map file over DAP**, bypassing DWARF — that fallback being under our control is why the plan is acceptable to carry.

- **SOL-G9 — Emulator input model contradicted hardware latency. [RESOLVED 2026-07-26 — §9, §14.5, G11, D102.]** Accepted, and **D66 sharpened it**: with acquisition corrected to ≈400 Hz, "present pad state each frame" cannot reproduce sub-frame transitions, mid-frame change-IRQ timing, or a press-and-release within one frame (possible at 2.5 ms granularity) — and games will use the change IRQ, so its timing must match. Replaced with a **timestamped `(cycle, device, state)` event queue** applied during the scanline loop like raster and blitter events. The **acquisition cadence is modelled rather than the TH protocol**, keeping oito's sequencing internal while making observable timing correct; keyboard and mouse events carry their own PS/2 timestamps. **Two tiers:** Tier 1 may quantise to ~2.5 ms boundaries, Tier 2 to exact cycles — **frame-granular input is conformant at neither**.

- **SOL-B1 — VRAM port semantics incomplete. [RESOLVED 2026-07-26 — §5.1, D103.]** Accepted: the CPU's only path to VRAM had "1/2/32/64/…" where a specification belongs. **All eight stride codes defined** (1, 2, 4, 8, 32, 64, 128, 256 — chosen to match a name-table cell, a 4bpp tile row, an OAM entry, a whole tile and a name-table row), plus: **every successful read *or* write post-increments exactly once** after the transfer; **there is no read buffer** — `VRAM_DATA` returns the byte at the current pointer, stated explicitly because NES-style ports *do* buffer and an implementer with that background would guess wrong; the pointer **wraps mod 128 KB**; `VRAM_ADDR2` bits 1–7 are ignored and read 0; **the address is latched at access start**, so writing the pointer during an RDY stall cannot redirect the in-flight transfer; and back-to-back accesses arbitrate independently.

- **SOL-B2 — Palette port edge cases undefined. [RESOLVED 2026-07-26 — §5.1, D104.]** Accepted, and one part of it is player-visible rather than merely internal. Pinned: **`PAL_INDEX` masks to 6 bits**; **increment occurs only on a `PAL_DATA_HI` write and wraps 63 → 0** (so the LO/HI pair is the natural unit and a stray LO write cannot desynchronise the index); **reads never increment**, allowing read-back without disturbing the pointer; **LO and HI are independently visible**, keeping the port stateless at the cost of a transient colour if a game separates the writes. The significant decision: **writes take effect at the very next composited pixel**, because palette RAM is read per pixel — which is what makes **mid-scanline palette swaps** work as a way to exceed 64 on-screen colours. Emulator consequence stated explicitly: **sample palette state per pixel, never cache it per line**, or those effects silently break.

- **SOL-B3 — Pattern-base addition could leave VRAM. [RESOLVED 2026-07-26 — §6.6, D105.]** Accepted, and the arithmetic shows it is routine rather than exotic: a **12-bit tile index alone spans the whole 128 KB** (4096 × 32 B), so *any* non-zero pattern base can carry a high index past 17 bits — tile 4000 with a 2 KB base already overflows. Resolved with **one uniform rule: every VRAM address computation wraps modulo 128 KB**, covering pattern bases, name-tables, sprite patterns, cursor tile, text char-map, blitter and CPU port. **No clamping or invalid-tile behaviour** — wrapping is what the 17-bit address bus does naturally, so it is free and deterministic, while clamping needs comparators that buy nothing. The consequence is documented rather than hidden (base and index spaces overlap and alias), with the asset packer warning when a bank's tile range would wrap. This also consolidates three separate wrap statements (SOL-A8, B1, A12) into one rule.

- **SOL-B4 — Vertical scroll had an unexplained ninth bit. [RESOLVED 2026-07-26 — §5.1, §6.1, §6.6, D106.]** I had flagged this as the one item I might dispute; on checking, **the review is right and I was wrong**. The name-table is **256 px tall**, which 8 bits addresses exactly — bit 8 of Y had nothing to point at. (X genuinely needs 9 bits for the 512 px width, and *sprite* X/Y remain 9-bit for off-screen positioning at origin (32,32) — those are unaffected.) **Y scroll is now 8-bit**, with **`$4013` and `$4019` reserved** (writes ignored, reads 0). Repurposing the bit for a 512-px-tall plane was considered and rejected: it would **double BG name-table VRAM from 4 KB to 8 KB per plane** and raise fetch bandwidth for a capability nothing has asked for — leaving it reserved keeps that option open at zero cost.

- **SOL-B5 — OAM DMA source encoding was misleading. [RESOLVED 2026-07-26 — §5.1, §6.6, G43, D107.]** My D39 wording was sloppy and self-contradictory: it said the register "supplies A15:A10" while the accompanying formula `(value & $3C) << 8` actually used **bits 2–5 as A10–A13**, with A14/A15 forced zero because only 16 KB exists. Taking the review's better option, the field is **re-encoded as a plain 1 KB block number in bits 0–3 (0–15), address = `block << 10`** — one shift from any address (`addr >> 10`), rather than requiring callers to pre-shift *and* track which bits were live. **All 16 values are valid** (16 KB is exactly sixteen 1 KB blocks), so there is no illegal encoding to define. Nothing had been built against the old form, so there is no compatibility cost.

- **SOL-B6 — "Partial OAM update" could only update the prefix. [RESOLVED 2026-07-26 — §5.1, §6.6, D108.]** A good catch that tested a **claim** rather than a mechanism: D39 advertised that a game moving six sprites "pays ~32 cycles instead of 683", but with only `OAM_DMA_LEN` a transfer can refresh a **prefix and nothing else** — worthless for sprites at indices 40, 41 and 90. Added **`OAM_DMA_OFS` ($4065)**, a starting entry index (0–127) driving **source and destination together**, which keeps the shadow buffer and OAM in lockstep without a second register and makes the advertised saving real **at any index**. Semantics pinned as the review asked: **`LEN` 0 = all 128, 1–128 exact, 129–255 clamp** (clamping rather than wrapping, matching D99), and **`OFS + LEN` past entry 127 wraps within OAM** — falling straight out of the mod-128 KB rule of SOL-B3.

- **SOL-B7 — Shadow-OAM refresh timing was ambiguous. [RESOLVED 2026-07-26 — §6.5, §6.6, G46, D109.]** The loose end left by my own D41: "once per frame during VBLANK" names no line or cycle, and "OAM DMA takes effect on the current frame" contradicts it for a DMA issued during active display, where it holds only for lines not yet drawn. Pinned to a single named event — **the snapshot occurs at the start of line 224** — from which everything follows exactly: **frame N renders from the shadow captured at line 224 of frame N−1** (so VRAM-port writes land next frame), while **OAM DMA writes the shadow immediately** and is therefore visible on **all lines rendered after the burst completes**. The consequence is now documented rather than discovered: a **mid-frame DMA tears**, sprites above the raster showing old positions and below new — which is why the SDK issues DMA in VBLANK. Both the snapshot and the DMA completion are ordinary schedulable events in the emulator's scanline loop.

- **SOL-B8 — Sprite-overflow status cleared before software could observe it. [RESOLVED 2026-07-26 — §5.1, §6.6, G37, D110.]** A design bug rather than a wording gap: `STATUS.3` reported "this frame" yet was **cleared at VBLANK start** — exactly when a game first gets to inspect the completed frame — so it was readable only by polling during active display. Now it **reports the completed frame and clears at the start of the next active frame (line 0), or on a write-1** (matching the `IRQ_STATUS`/`INPUT_STATUS` idiom and allowing sub-frame measurement). The reason this matters beyond tidiness: per-frame overflow detection is how a game implements **sprite multiplexing** — rotating OAM priority between frames so excess sprites flicker instead of vanishing — so the original semantics would have quietly made a standard retro technique unusable.

- **SOL-B9 — Cursor 16×16 storage contradicted "one tile". [RESOLVED 2026-07-26 — §5.1, §9.2, §15.14, D35, D111.]** Plain arithmetic contradiction in my D35: a **16×16 4bpp image is 128 bytes** while a **tile is 32** — the cursor could not be "one VRAM tile" *and* offer a 16×16 size, and the claim was repeated in four places. Now: **one tile in 8×8 mode, four consecutive tiles in 16×16**, ordered **row-major (top-left, top-right, bottom-left, bottom-right)** — reusing the multi-tile sprite convention of §6.6 so the system has a single layout rule. The quad must be **4-aligned**, so the index's low 2 bits are **ignored** in 16×16 mode, keeping the fetch trivial. **No H/V flip is provided**, stated explicitly since a pointer never needs it. Left unfixed this would have rendered 32 bytes of a 128-byte image — a very visible bug.

- **SOL-B10 — Mouse/cursor arithmetic unspecified. [RESOLVED 2026-07-26 — §9.2, §5.1, D112.]** All seven sub-items pinned, on the principle that **cursor feel is immediately noticeable to players**, so divergence here is user-visible rather than academic. **`CURSOR_SCALE` is 4.4 fixed-point** (1.0 = `$10`, range 0.25–15.9) with **0 treated as 1.0** — a pointer frozen by a zeroed register is a nasty failure — and **fractional remainders retained between packets**, which is what makes slow, fine positioning work. **Acceleration** is one threshold and one multiplier (`|delta| > 4` ⇒ ×2). **Truncate toward zero, saturate at bounds.** **Mouse Y is inverted on input** (PS/2 counts +Y up) and **overflow bits mean "discard this delta"**. **D-pad fallback ramps 1 → 4 px/frame after 250 ms**, diagonals at full rate. **`MOUSE_STATUS` bits 1–3 clear on reading that register itself**, naming which read "since last read" meant. **Reading `MOUSE_X_LO` latches X_HI and Y**, so a packet arriving mid-sequence cannot tear the coordinate pair. **`MOUSE_WHEEL` saturates at ±127** and clears on read.

- **SOL-B11 — Text map dimensions and stride not fixed. [RESOLVED 2026-07-26 — §6.8, §5.1, D113.]** Accepted: I wrote "always cols × 28" in D40 without noticing `cols` varies **32/40/64/80** across the resolution and narrow-mode combinations — leaving the row stride undefined and making a live mode switch reinterpret the same VRAM bytes as a different grid. Fixed by pinning **one stride: 80 cells (160 bytes) per row in every mode**, a fixed **80 × 28 = 4,480-byte** region, with narrow modes using the leftmost `cols` cells. The property this buys is worth the memory: a mode switch changes only **how many cells are displayed, never where a cell lives**, so text at (col 5, row 3) keeps its address in all four configurations and no re-layout is needed. Also pinned: **no horizontal or vertical wrapping**, **unsigned 0–255 scroll shifting content up/left** (incrementing Y scrolls credits upward), and **off-screen cells are not fetched**, so scrolling costs no extra bandwidth.

- **SOL-B12 — Firmware could not write the default font bank. [RESOLVED 2026-07-26 — §5.1, §6.8, D114.]** A real hole in my G45 design: the font port was hard-wired to the **cart bank**, while §11.1 requires the boot firmware to load the region charset into **bank 0** — an impossibility as written. Added **`FONT_ADDR_HI` bit 7 as a write-bank selector**, deliberately **independent of `TEXT_CTRL.font_sel`** (the display bank), which is independently useful: a game can rewrite the cart font while the default is on screen. The important half is the gate — **bank-0 writes are honoured only while the boot overlay is active (`BOOT_SRC ≠ 2`) and are silently ignored after handoff** — because that is what actually enforces G45's promise that the default font survives for no-cart and error screens; without it a game could overwrite bank 0 and break system text. The gate reuses an existing one-way state rather than adding a mechanism, and post-handoff writes are a **no-op rather than an error**, so hardware and emulator behave identically.

- **SOL-B14 — IRQ pending/mask semantics needed a state machine. [RESOLVED 2026-07-26 — §10, §5.1, G13, D115.]** Accepted: "ORs enabled+pending sources onto IRQ̄" left seven software-observable behaviours undefined. Now pinned: **`IRQ̄ = NOT(any(IRQ_STATUS & IRQ_ENABLE))`, purely combinational**; **masked events still set status** (the mask gates assertion, not recording — which is what makes a source pollable with its interrupt off, the basis of D44); **unmasking an already-pending event asserts immediately**, preventing lost interrupts; **a same-cycle set beats a W1C clear**, since silently losing an event would be an unreproducible bug whereas the worst case here is one spurious re-entry; **`IRQ_STATUS` bits are edge-latched and cleared only by W1C** (a level-derived VBLANK bit would re-set the instant it was acknowledged, storming), while **`STATUS`.0–1 are level** (raster position) and **`INPUT_STATUS`.2 is level, re-latching while keyboard FIFO data remains**, so handlers must **drain the FIFO, not merely acknowledge**; and **raster-compare fires at the start of the compared line**, never retroactively, with values > 261 never firing.

- **SOL-B15 — Input FIFOs and maps lacked capacity and recovery rules. [RESOLVED 2026-07-26 — §5.1, §9.1, D116.]** Accepted, and one sub-point was a **design flaw rather than a missing number**: a one-byte `KBD_MAP_IDX` cannot distinguish extended Set-2 codes, so **`E0 4B` (right arrow) collided with `4B`** — and the arrow keys are precisely what the D34 key→joypad injection exists to map. Fixed with **bit 7 as the `E0` prefix flag, giving 256 map slots**; `KBD_MAP_VAL` gains **bit 4 to target the `_EXT` register** so X/Y/Z/Mode are reachable, with **$00 = unmapped**. Also pinned: **16-byte FIFO** (ample at ≈2.5 ms/frame against a VBLANK drain), **overflow drops new bytes** rather than overwriting — never corrupting a partially-consumed sequence — with a **W1C sticky flag** (the missing clear operation); **the lower-numbered port owns the FIFO** when two keyboards are attached; and **hot-unplug flushes the FIFO, clears `present` and clears all injected joypad bits**, so a yanked cable cannot leave a button stuck on.

- **SOL-B16 — Hit-test sampling time undefined. [RESOLVED 2026-07-26 — §9.2, §5.1, D117.]** Accepted: "once per frame" named no event, and the sampling instant determines which scroll and OAM state the result reflects — so two implementations would report different tiles under the same pointer. Pinned: **the sample is taken as the raster reaches the pick point**, latching what the compositor computed at that pixel (free, since the feature already taps the compositor, and it inherently captures the right scroll/OAM/palette state). **Pick coordinates are latched at line 0**, so mid-frame `PICK_X/Y` writes apply **next frame** — without which a game could request a point the beam had already passed and get an unreproducible answer. **`HIT_STATUS`.5 sets on sample and clears each frame**, giving a defined "no result" when the point lies outside the active area, and **results persist through VBLANK**, the natural time to read after a click. Deliberately the same timing idiom as SOL-B7.

- **SOL-B17 — Blitter figures needed a conformance workload. [RESOLVED 2026-07-26 — §6.5, §6.1, §15.8, D118.]** Accepted: "~1,187 / ~406 tiles/frame" had been quoted since the earliest conversations as if specified, but it was the output of an **unstated calculation** — no copy mode, tile size, arbitration assumption or concurrent sprite/text load — and **SOL-A8 has since changed the blitter itself** (pitch registers, per-nibble transparency, odd-edge RMW), so the figures describe a machine that no longer exists. Retired and replaced by a **defined benchmark** (opaque tile copy, 8×8, pitch 0, both BG planes, text off, zero sprites) with **guaranteed minimums: ≥1,000 tiles/frame interleaved, ≥350 blanking-only**, derived from the SOL-A9-corrected bandwidth table at 64 B of bus per tile. Everything outside that workload is **explicitly labelled an estimate** (transparent/masked modes cost more; sprites and the text layer reduce spare cycles). One consequence worth noting: a full-screen redraw (1,120 tiles) now sits **near the guaranteed floor rather than comfortably inside it**. Same move as SOL-E15 — a confident number replaced by a specification plus its measurement condition.

- **SOL-B18 — Reference-emulator accuracy goal conflicted. [RESOLVED 2026-07-26 — front matter, §6.5, §14.5, D119.]** The contradiction had been present since the document's first line — "non-cycle-perfect emulator" in the purpose statement against "cycle-accurate mimicry" in §14.5 — and survived every revision. Resolved with the review's two tiers, now normative: **Tier 1 (compatibility)** is what "the reference emulator" means and what the **golden conformance ROMs validate** — instruction-correct CPU with aggregate RDY stalls, scanline-timed VDP with per-pixel palette sampling, the line-224 shadow-OAM snapshot, pick-pixel hit-testing, sample-accurate APU, budget-driven blitter, and ~2.5 ms-quantised timestamped input; **Tier 2 (cycle-exact)** adds exact fetch scheduling, stall counts, mid-scanline effects and DMA/steal placement, and is **explicitly not required for compatibility**. This also gives a home to tiers that were already being used informally — SOL-G9 had invented "Tier 1/Tier 2" for input timing with nothing to reference — and collects the campaign's accumulated timing decisions in one place.

- **SOL-H1 — Status materially overstated. [RESOLVED 2026-07-26 — front matter, D120.]** The review's headline judgement, **accepted before any other item was touched**: the front matter's "all 53 register entries dispositioned / sufficient to plan and build / campaign complete" was withdrawn when SOL-A1 was registered. The campaign then vindicated the criticism — a large share of SOL findings were **defects in text previously marked "resolved"**, several of them introduced by earlier remediation. The final wording is honest in both directions: it states what *is* specified (memory map, register file, subsystem behaviour, BOM) and carries an **explicit outstanding-work table** (CH7035B and AD725 qualification, prog8 ROM-ability, typed symbols, debug-info fixtures, jamming validation, the 144-pin table, the licensing review, and the closure package). The review's own sentence is preserved in the document: **a disposition log records that decisions were made, not that they are correct.**

- **SOL-H2 — Separate normative contract from rationale/history. [ACCEPTED 2026-07-26 — scheduled, D121.]** Diagnosis agreed: **§16 (120 decisions) and §17 (135 gap entries) now outweigh the normative content**, and because they repeatedly restate superseded values they actively **hide contradictions** — not hypothetically, since several SOL findings were conflicts *between* a "resolved" gap entry and the section it claimed to resolve. The remedy is a **document split**, specified now and executed as a dedicated pass **after this review concludes** (rushing a restructuring at the end of an 80-item campaign is how fresh inconsistencies are introduced):
  - **`re8-console-spec.md` becomes purely normative**, ordered per the review: (1) machine-visible behaviour, (2) electrical interfaces and BOM, (3) timing, (4) file/tool ABI, (5) conformance tests.
  - **`re8-design-history.md`** receives §16, §17 and the superseded-variant narratives, linked from the spec — history records *why*, and stops interleaving with *what*.
  - **Standing rule to prevent recurrence:** the normative document **states only current values**; "X was Y, now Z" phrasing moves to history.
  - **Sequenced with the §J closure package** (register CSV/JSON, golden vectors, conformance ROMs), since both are the same kind of work — extracting structured artefacts from prose.

- **SOL-H3 — Use RFC-style requirement words. [RESOLVED 2026-07-26 — front matter + targeted edits, D122; systematic pass folded into SOL-H2.]** Accepted: requirements and commentary shared one voice, so a reader could not tell what was binding — and every intensifier the review named ("in practice", "essentially for free", "comfortable", "every display", "zero cost", "harmless") appeared here, repeatedly. Done now: an **RFC 2119 convention note** in the front matter (MUST/MUST NOT/SHOULD/MAY used **only** for requirements) and **replacement of the flagged phrases with measurable limits** — e.g. VRAM timing now states "≈36 ns of margin", the breakpoint path "≈61 ns of margin", the hit-test cost "one coordinate comparator plus the latches listed in §5.1", and the RDY-stall text bounds the stall instead of saying "a few cycles". The **systematic keyword conversion is deferred to the SOL-H2 split**, where each normative statement is classified as it is relocated — avoiding churn on text that is about to change file.

- **SOL-H4 — Performance claims without test definitions. [RESOLVED 2026-07-26 — front matter, §4, §6.1, §8.3, §15, D123.]** Largely swept by the campaign already (SOL-E15 quantified the cadence, SOL-B17 replaced the blitter figures with a benchmark, SOL-H3 bounded "a few cycles"); what remained was the durable part. **Standing rule added: every performance figure MUST carry a stated workload or the label *estimate*.** The PCM cost keeps its number but now travels with its conditions — **4 voices, 8-bit, 48 kHz, 16-byte bursts ⇒ ≈2.7 % rising to ≈6 %** with arbitration overhead. The CPU's "~1.8–2.7 MIPS" is retained but **labelled as arithmetic from cycle counts, not a benchmark**. **Cross-machine comparisons (Genesis 68000, Amiga 500, Lynx, "premium 16-bit arcade") are deleted rather than qualified** — a technical specification has no business comparing itself to hardware it has never been benchmarked against; they survive only in the G28 page-refresh punch-list, where marketing framing belongs.

- **SOL-H5 — Stale/contradictory phrases. [RESOLVED 2026-07-26 — §2 D11, §7, §5.1, D124.]** Three of the six had already been fixed in passing during the campaign (I²S-to-CH7035B by SOL-E12, `STATUS.3`'s clear point by SOL-B8, the accuracy-goal conflict by SOL-B18). The remaining three: **"zero-latency execute-in-place" → "execute-in-place without a preload step"** — the named NOR has 70 ns access, and the genuine advantage over SPI flash is needing no copy-to-RAM, not zero latency; **"digital fan-out costs almost zero current" deleted** — it contradicted §7's own analog-buffer requirement, since SOL-E9 specifies three buffer paths precisely because one source *cannot* drive five outputs, and it was an unmeasured claim of the kind SOL-H4 now forbids; and the **reset-state exception list corrected** to the single genuinely non-zero default (`SAVE_CTRL`.1 = 1), since listing `CURSOR_CTRL` source = 0 as an "exception" was meaningless when 0 is the general reset value — with the two load-bearing zeros (`BOOT_SRC`, `BOOT_FLASH_WE`) noted separately for clarity.
